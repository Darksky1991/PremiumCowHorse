## 关键决定（执行中的裁定）

- **拖放只管理条目**：dragstart 只设自定义 MIME `application/x-pch-node`；真实节点、状态行不接受放置；系统拖入的 `dropEffect` 只用 copy / link（move 会让资源管理器移走原文件）。主进程没有任何写文件的 API。
- **监听的重建由渲染端负责**（Task 3）：监听自行失效后主进程只删除记录；渲染端收到属于当前集合的 `vfs.changed` 后重发完整集合。原实现的代价：重发时目录尚不存在则不会再自动重建。**修复第 1 轮（Task 10 审查）**：监听集合只取列表已就绪的目录（`data/vfs.ts` 的 `watchableUris`），出错的目录移出集合，列表恢复后重新进入集合并触发 `vfs.watch`，监听得以重建。
- **`refetchOnWindowFocus: 'always'`**（Task 5）：全局默认 `staleTime: Infinity` 下计划写的 `true` 不会触发。**被最终审查推翻**：focusManager 默认只监听 `visibilitychange`，Electron 中 Alt+Tab 不触发，`'always'` 也无效；改法见下文「最终审查修复」I1 + I2。
- **`app/` 不依赖 `data/`**（Task 5，lint 规则）：需要数据的组件放在 feature 中；Task 5 的占位工作区名称放在 shell feature，Task 9 用 `features/workspace` 替换。中间状态（Task 5–8）暂时没有「新建工作区」入口，已接受。
- **失效链接**（Task 2 → 6）：lstat 失败的降级链接没有 `target`，资源树按失效链接处理（不可展开）。
- **添加条目的类型**（Task 7）：真实子项的类型取自节点（目录与指向目录的链接为 folder）；系统文件先按 folder 添加，`ENTRY_KIND_MISMATCH` 时改按 file，不新增 IPC。
- **状态行**（Task 6 → 7 / 8）：不可拖动、不接受放置、没有右键菜单、F2 / Delete 无效；可被选中（错误行上 Enter = 重试）。
- **空状态的放置在范围内**（Task 7）：界面文案写着「拖到这里」，因此空状态也接受系统拖入。
- **虚拟文件拖入**（Task 7 审查 I1）：可能固定 %TEMP% 副本，需要真机验证与需求方决定，不在修复循环中处理，记入 doc 8.2 / 19 节的已知限制。
- **删除当前工作区**（Task 9）：主进程删除不改变「当前工作区」，渲染端先 `activate('default')`、成功后再删除；新建后切换失败也关闭对话框，避免重复创建。
- **重新获取失败时错误优先**（Task 10）：e2e 发现展开中被删除的目录一直显示旧列表（TanStack Query 在重新获取失败时保留旧 data，`useDirectories` 先看 data）。改为错误优先（`data/vfs.ts` 的 `directoryState`，先写失败的单元测试）。这改动了 Task 5 的代码，单独提交。

- `pnpm typecheck && pnpm lint && npx prettier --check . && pnpm test && pnpm build && pnpm test:e2e` 全部通过：vitest 21 个文件 196 项（M1-1 结束时 85 项）；e2e 23 项（M1-1 结束时 7 项）。

- 既有 e2e 的偶发失败：`workspace switcher` 用例约 1/5 失败。原因：上一个菜单的关闭动画结束前再次点击切换器，菜单重新打开但焦点留在按钮上，随后的 Esc 被忽略（诊断用例确认）；另有一处「不存在」断言在菜单渲染前就空洞地通过。改为每次打开前等旧菜单从 DOM 中移除、打开后再断言，连续 8 次通过。
- 系统级整窗截图共 5 张，已查看：浅色 ja、深色 ja、浅色 zh-CN、深色 en、紧凑密度浅色 ja（未拍深色 zh-CN / 浅色 en / 紧凑深色等其他组合）。截图用的是改写自 `scripts/os-screenshot.mjs` 的临时脚本（同样的 CopyFromScreen 整窗截取，另外先经 IPC 添加条目、展开并制造一个错误行）；原脚本只能截空的工作区，不能准备内容。

### 待需求方决定

1. **监听句柄阻止上级目录改名 / 移动**（I4，已实机验证）：(1) 维持现状（实时更新优先）；(2) 每个条目根只建一个递归监听（`fs.watch(root, { recursive: true })`，只阻止条目根的上级改名）；(3) 不使用 `fs.watch`，改为聚焦 / 展开时刷新 + 可选轮询（不阻止任何改名，失去实时性）。
2. **虚拟文件拖入**（未实机验证）：副本由 Chromium 在浏览器进程中写入，且只在我们 dragover 接受（`preventDefault` + `copy`）之后、drop 时才写；拖放事件中拿不到路径，dragover 阶段分不出是否为虚拟文件。选项：(a) 接受 Chromium 写临时副本（应用自身不写），照常添加（现状）；(b) 写出副本后拒绝固定临时路径（副本仍产生；识别方式可考虑 Chromium 临时子目录的命名特征，需实机确认）；(c) 完全不接受系统拖入，只保留系统对话框。
3. **`system.openPath` 会直接执行可执行文件**（`.exe` / `.bat` / `.lnk` 等，`shell.openPath` 的行为，计划如此）：是否对可执行类型先确认或禁止。
4. **隐藏文件只按名称以 `.` 开头判断**：Windows 的隐藏 / 系统属性需要原生 API（koffi），是否需要、何时引入。
5. **新增条目总是追加到父节点末尾**：`entry.add` 没有位置参数，拖放时 before / after 的画线只决定父节点，可能误导；是否给 `entry.add` 增加位置参数。
