## 编码判断

- **对比实验**（设计第 4 节，114 样本 = 19 种编码 × 6 种形态）：`encoding-japanese` 65.8%、`jschardet` 77.2%、`chardet` 83.3%、`chardetng-wasm` 76.3%、前置判断 + chardetng 90.4%、**自写（前置判断 + 常用字区打分）93.0%**（只错在无 BOM 的纯中日文 UTF-16）。因此不引入检测库（包括需求方曾同意的 `encoding-japanese`：对中文无效），无依赖、无 WASM、不放宽 CSP。
- **验收样本**：T2 的 111 个样本（由另一个 agent 编写，含半角片假名、JIS 第二水准、GB18030 四字节、Big5 二级字、纯汉字短文本、CSV、混入 cp1252 符号的英文）：**111 / 111**（7 个本身有歧义的样本按「可接受集合」判定，该集合由 `TextDecoder` 计算，不由人工判断）。
- **审查者独立留出集**（T3 审查，opus，在 scratch 构造，不入库）：set1 **60 / 60**；set2 **394 / 410（96.1%）**，其中半角片假名 40 / 40、日文（含纯汉字）160 / 160、Big5 80 / 80、大文件末尾抽样 5 / 5，未见过拟合迹象。
- **修复后 cp1252 短文本误判**：修复前 16–80 字节、含 1 个重音字符 / 弯引号的英文有 20 字符时 37% 被判成 UTF-16；修复后合成样本 0 / 2400（再审 0 / 3000、369 / 1800 → 0）；纯 CJK UTF-16 的召回不变。
- 阈值（`top < 8` 或差距 `< 4` 判为 `guess`）与 3 条规则是看到失败样本后调的，有过拟合风险，已由上面的留出集验证。

### 1GB 日志实测（应用内，一次性 Playwright 脚本，已删除）

文件：`huge.log`，10,800,000 行 × 100 字节 = 1,080,000,000 字节（约 1.0 GiB），本地 SSD，默认设置（`preview.maxTextSizeMB` 默认 50，最大 500，故 1GB 文件一定先进入部分模式）。连续 3 次运行：

| 项目                                                              | 结果（3 次）          | 目标 / 说明                                                                                                          |
| ----------------------------------------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 首屏：点击文件 → 末尾行可见（部分模式，读末尾 4MB 窗口）          | 888 / 928 / 905 ms    | 设计目标「首屏 < 300ms」**未达标**（见下）；状态栏显示「末尾 4 MB のみ表示（全体 1 GB）」，窗口内 41,943 行          |
| 点「すべて読み込む」→ 全量索引完成（10,800,000 行）               | 4922 / 4907 / 4974 ms | 约 **217 MB/s**（1.08GB / 4.9s），低于设计「≥ 300MB/s」；含 1MB 分块的开-读-关、UTF-8 全程校验、IPC 进度与 20ms 轮询 |
| 全量索引后拖动滚动条拇指到轨道中点 → 行号与内容一致的中间行已渲染 | 18 / 18 / 17 ms       | 目标「任意位置跳转 < 100ms」达标；第一可见行 5,400,094（总行数 10,800,000 的 50.0%）                                 |

对照与说明：

- **首屏 ~0.9 秒**未达到 300ms：测量包含 Playwright 点击 → 资源树 → 容器 sniff / 匹配 → `doc.open`（主进程等第一块 1MB 索引 + 读 4MB 窗口建索引 + 编码抽样）→ 解码 → 渲染 → 轮询到末尾行可见的全过程，不是单一环节；没有逐段打点，**瓶颈在哪一段未验证**。500MB 以下的文件走全量模式，首屏不读 4MB 窗口（本任务未测）。是否需要优化由需求方 / 控制者决定。
- **全量索引 217MB/s < 300MB/s**：纯引擎 1180MB/s，差距在主进程的分块读取 + UTF-8 校验 + 事件。这是 1GB 的读取 + 校验，而日常使用中不点「すべて読み込む」就不会发生（默认只读 4MB）。目标按设计写为「≥ 300MB/s（SSD）」，实测未达，**记为已知差距**，不在本任务修改。
- 跳转 18ms 是全量索引完成之后的数字；索引进行中跳转到尚未索引的区域按设计受限于已索引范围。

## 控制者的决定（Ruling）

台账中的 Ruling 与各任务的决定：

1. **`DOC_ENCODINGS`（shared zod）与 `ENCODING_LABELS`（text-engine）两份列表**：text-engine 不依赖 shared、shared 不依赖 text-engine，所以重复并用主进程的类型级相等测试保证一致（代价：一条额外测试）。
2. **T2（样本库）与 T3（检测器）派给不同的 agent**：设计第 4 节的偏差对策（样本与打分同一人写会偏乐观）。
3. **不引入 `encoding-japanese`**（对比实验 66%、无中文支持；自写 93%）：将来需要时作为 text-engine 的依赖再加。
4. **整个计划一份 devDoc 记录**（本文件）而不是每个任务一份：CLAUDE.md 的「每个任务」按计划任务集解读，以前的计划同样如此（代价：以后要拆可拆）。
5. **读取进行中无法改名上级目录**（T4）：接受为已知限制（与目录枚举同类，doc 7.1）；T6 的 e2e 改为：索引期间改名文件成功、上级目录在读取间隙（重试 ≤ 2 秒）成功、索引完成后总成功。
6. **缺失时继续轮询**（T5，纠正控制者自己在补充中的错误）：轮转后同名文件重新出现必须无需 F5 就恢复（Review Focus 2）；代价：文件消失期间每个间隔一次 stat。
7. **`manifest.handlesMissing`**（T6）：文本插件自己处理「文件已不存在」，保留缓存行并显示提示，而不是被容器的 not-found 面板替换（设计 3.6 要求）；代价：SDK 多一个可选标志，可删。
8. **最终修复波的范围**：Important 1–2 加上用户可见且小的 minor（块缓存每行开销、epoch 变化清错误、卸载时 flush 未保存的 viewState、部分模式 → 读取全部的位置、reset 立即丢缓存、状态栏错误用 `describeError`、加强 RF3 e2e），代价：少量额外工作。
9. **tab / viewState 的可选 `uri`**（最终修复波）：卸载时的 viewState 写入刚离开的历史项，否则 flush 会落在新位置；代价：小范围 reducer 改动，可回退。

各任务的实现决定：

- T1：`LineBlock.start` 为行号，`truncated` 为绝对行号；text-engine 的 lint 用 `no-restricted-imports`（只允许相对导入）+ `no-restricted-globals`（`eslint-plugin-boundaries` 管不到外部包，见 `knowledge/libraries.md`）；2000 行上限在 IPC 强制；`finish(windowEnd)` 必须等于 `indexedTo`；额外文件 `newline.ts`、`chunk-source.ts`。
- T2：`expected/` 放 UTF-8 原文；eslint 忽略 `**/*.test-helper.ts` 的 `node:fs`；`.prettierignore` 忽略 fixtures；`fixtures/.gitattributes` 设为 binary（保留 CRLF）；日志样本 400 行。
- T3：`samples[0]` 从文件开头、其余跳到第一个 LF；顶分 < 8 或差距 < 4 为 `guess`；无正分 → UTF-8 guess；`preferred` 只用于平局（默认日文优先）；二进制判断：含 NUL 或 >5% 可疑控制字符。
- T4：大小相同但 mtime 变 → reset；`doc.open` 等第一个 1MB 索引完才返回（事件不早于应答）；UTF-8 校验忽略末尾不完整字符；缺失只通知一次、再现 → reset；开头窗口文档忽略追加；`DocLineBlock` 与 `LineBlock` 类型测试相等；错误码 `DOC_NOT_FOUND`。
- T5：plugin-sdk 重复声明文档类型（与 shared 类型测试相等，不依赖 shared / text-engine）；`DocChange` 带刷新后的信息；宿主侧按 generation 丢弃过期 `readLines`（`DocStaleError`）；`viewAs` / `canViewAs` 按标签；空文件不 sniff 直接兜底；主进程 `resetOwner`（重载 / 崩溃）与 `releaseOwner` 分开；关闭后不再发 `doc.changed`。
- T6：日志类打开自动跟随末尾；部分模式隐藏行号栏。
- 最终修复波：重置但没有新信息时，插件暂停读取、显示占位行，直到信息到达（刷新一直失败时会一直停留，待需求方确认）；RF3 e2e 约 200MB，断言改名发生在索引期间；item 2（追加后最后一行陈旧）只有单元测试。

- 行与块：孤立的 `\r` 不算换行；字节级截断可能切开多字节字符（显示末尾 U+FFFD）；`maxBytes` 提前停止时多扫一行；UTF-16 窗口起点奇偶未检查（主进程保证）。
- 主进程：`handle.close()` 的错误会盖住读取错误；目录 → EISDIR → `UNKNOWN`；进度节流没有收尾的最后一次发送；`setEncoding(null)` 同一编码不重启 UTF-8 校验；`released` 集合只增不减；`doc.changed` 在 open 应答之前会被丢弃；轮询间隔设置变化要一个周期后才生效；`did-start-navigation` 在提交之前触发（旧页面可能打开文档 / 被中止的导航会关闭文档）；映射的网络盘按本地间隔轮询；F5 不重新 sniff；sniff 失败时兜底插件显示文件信息而不是错误。
- 界面：text→info 视图切换依赖插件自己关闭；空文件→有内容后 F5 重新挂载有闪烁；`use-visible-lines` 的调度（快速拖动、`DocStaleError`）只有 e2e 覆盖；块缓存的 drops 只保留最近 64 条；reset 导致的 epoch 加两次（无害）；`awaitingInfo` 占位行在刷新持续失败时一直显示（待需求方确认，见上）；viewState 写入在两个栈顶共享同一 URI 时优先写回退栈顶；200MB 的 RF3 e2e 较慢，在极快的磁盘上理论上有竞态。
- 本任务的观察：部分模式状态栏的行数是窗口内行数，只靠「只显示 …」文字区分，容易被理解为文件总行数。
