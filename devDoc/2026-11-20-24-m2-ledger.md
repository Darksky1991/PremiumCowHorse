### S1 Playwright 能否访问 `WebContentsView` 的页面

- 做法：视图加载 `pch-web://scope1/page.html` 后，查看 `electronApp.windows()`、`electronApp.context().pages()`，对视图页面用 `page.title()`、`page.locator('#t').textContent()` 断言；另试 CDP（`context().browser()`）与主进程侧 `webContents.executeJavaScript`。
- 结果：**可用**。视图页面出现在 `app.windows()` 与 `context().pages()` 中（顺序：宿主页在前，视图页在后），Playwright 的 `Page` API（`title`、`locator`、`evaluate`）正常工作。`context().browser()` 为 `null`（Electron 模式下没有 Browser 对象，`newBrowserCDPSession` 不可用）。主进程侧 `electronApp.evaluate(() => view.webContents.executeJavaScript(...))` 同样可用，作为备选。
- 对计划的影响：Task 7 / 8 的 e2e 用 `app.windows().find((p) => p.url().startsWith('pch-web:'))` 取视图页面并直接断言；不要假设 `app.windows()[0]` 以外的顺序，按 URL 找。注意 Playwright 的颜色方案模拟同样作用于视图页面（见 S2）。

### S2 视图中 `prefers-color-scheme` 是否跟随 `nativeTheme.themeSource`

- 做法：视图页面注册 `matchMedia('(prefers-color-scheme: dark)')` 的 `change` 监听；主进程依次设 `themeSource = dark / light / dark / system`，每次 300ms 后读 `matches`、`body` 的计算背景色、`change` 记录与 `performance.timeOrigin`（判断是否重新加载）。
- 结果：
  - 第一次运行（`_electron.launch` 默认参数）：宿主页与视图页的 `matches` 始终为 `false`、没有任何 `change` 事件。原因：**Playwright 的 `_electron.launch` 默认 `colorScheme: 'light'`，对所有页面模拟 `prefers-color-scheme`**（`playwright-core` 类型定义：「Passing `null` resets emulation to system defaults. Defaults to `'light'`」），掩盖了真实行为。
  - 加 `colorScheme: null` 后：**成立**。视图页面的 `matches` 与背景色随 `themeSource` 即时切换（dark → `true` / `rgb(32, 32, 32)`，light / system → `false`），`change` 事件依次为 `[true, false, true, false]`，`timeOrigin` 不变（没有重新加载）。宿主页同样跟随。
- 对计划的影响：Task 8 的 Markdown 样式与 mermaid 主题直接用 `prefers-color-scheme`，**不需要** `&theme=` 查询参数与主题变化时的重新加载。凡是断言深浅色的 e2e，`launch` 时要传 `colorScheme: null`（`e2e/support.ts` 现在没有传；需要时加参数，不要改变现有用例的默认行为）。已记入 `knowledge/testing.md`。

### S3 视图能否直接显示 `.pdf` 与 `.png`

- 做法：视图分别加载 `pch-web://scope1/sample.png`（200×120，左红右蓝）与 `sample.pdf`（手写的一页 PDF，一行文字），处理器返回 `Content-Type: image/png` / `application/pdf`；读 `document.contentType` 与图片尺寸，`webContents.capturePage()` 与系统截图各取一张。`webPreferences.plugins` 分别为 `false`（默认）与 `true`。
- 结果：**成立**，两种 `plugins` 设置结果相同。
  - PNG：Chromium 的图片文档（深色背景居中显示，`naturalWidth/Height` = 200×120），没有加载失败。
  - PDF：显示 Chromium 内置 PDF 查看器（顶部工具栏有下载、打印、更多按钮，文字正确渲染）；`document.contentType` 为 `application/pdf`；**不需要** `plugins: true`。`capturePage()` 能截到 PDF 内容（5.3.7 的截图替身可用于 PDF）。PDF 查看器的内部框架不出现在 `app.windows()` 中。
  - `capturePage()` 返回的是物理像素尺寸（400×300 DIP 的视图在 150% 下为 600×450），截图替身显示时要按 CSS 尺寸缩放（如 `background-size: 100% 100%`）。
- 对计划的影响：Task 7 的 html 插件 `match.extensions` 按计划追加 `pdf`、`png`、`jpg`、`jpeg`、`gif`、`webp`、`svg`、`bmp`（本次只实测了 png 与 pdf，其余图片格式未逐一验证，Task 7 的 e2e 至少覆盖 pdf 与一种图片）。插件名改为「ブラウザー表示」类文案（三语）。需在 Task 7 核实（未验证）：① PDF 查看器工具栏的「下载」按钮在 `will-download` 一律取消时的表现；② PDF 查看器的内部页面（扩展页）是否会被 `windows/security.ts` 的全局 `will-navigate` 处理或 `modules/web` 的导航判定误拦；③ 打印按钮（5.3.9 打印为推迟功能，查看器自带的打印是否放行由实现者决定并记录）。

### S4 Excel / Word 的 verb 行为（含 `UserChoiceLatest`）

- 做法：用 Office COM 在 scratchpad 生成示例 `spike-sample.xlsx` / `spike-sample.docx`（不碰用户文件）。对每个文件依次 `Start-Process -FilePath $env:PCH_TARGET -Verb $env:PCH_VERB`（verb = `Open` / `OpenAsReadOnly` / `ViewProtected` / `New`，另试不带 `-Verb`），等窗口出现后全屏系统截图（`CopyFromScreen`，DPI aware；`scripts/os-screenshot.mjs` 只截本应用窗口，不适用），记录窗口标题，并用「锁状态探针」判断打开模式；结束后按 PID 结束本次启动的 Office 进程（不保存；示例文件未被修改）。
  - 锁状态探针的对照实验（COM `Workbooks.Open(path, 0, ReadOnly)` / `Documents.Open(path, False, ReadOnly)`）：**以编辑模式打开时同目录出现所有者文件 `~$…`，只读时不出现**（Excel 只读时其他进程仍可写打开，编辑时拒绝写；Word 两种模式都拒绝写）。据此用「是否出现 `~$` 文件」判定编辑 / 只读。
  - 注册表 verb 命令（本机）：Excel `Open` = `EXCEL.EXE "%1"`、`OpenAsReadOnly` = `EXCEL.EXE /h "%1"`、`ViewProtected` = `/vp`、`New` = `/n`；Word `Open` = `WINWORD.EXE /n "%1" /o "%u"`、`OpenAsReadOnly` = `/h /n`、`ViewProtected` = `/vp`、`New` = `/n /f`。`OpenAsReadOnly` 与 `ViewProtected` 带 `Extended` 值（资源管理器中 Shift+右键才显示）。都没有 `ddeexec`。
- 结果：

| verb                       | .xlsx（Excel）                                                                                                  | .docx（Word）                                                                 |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `Open`（以及不带 `-Verb`） | **弹出系统的「选择一个应用以打开此 .xlsx 文件」对话框**（默认应用 Excel，「始终 / 仅一次」），Excel 未启动      | 同左（.docx 的选择对话框）                                                    |
| `OpenAsReadOnly`           | **以编辑模式打开**：标题 `spike-sample.xlsx - Excel`，无「Read-Only」，出现 `~$spike-sample.xlsx`、拒绝他人写入 | **以编辑模式打开**：标题无「只读」，「Editing」模式，出现 `~$ike-sample.docx` |
| `ViewProtected`            | 保护视图（标题 `… - Protected View - Excel`，黄色「PROTECTED VIEW / Enable Editing」栏），无 `~$` 文件          | 保护视图（标题 `… - Protected View - Word`），无 `~$` 文件                    |
| `New`                      | **以该文件为蓝本新建**：未保存的新工作簿 `spike-sample1`，内容与原文件相同，原文件未被占用                      | **以该文件为蓝本新建**：未保存的新文档 `Document1`，内容与原文件相同          |

- 补充发现：
  - **Windows PowerShell 5.1 的 `Start-Process` 没有 `-LiteralPath` 参数**（参数集只有 `FilePath`；doc 10.3 与设计 5.6.2、计划 Task 9 的写法会直接报 `A parameter cannot be found that matches parameter name 'LiteralPath'`）。
  - **`Start-Process -FilePath` 对路径做通配符解析**：同目录有 `見積[1] 案.xlsx` 与 `見積1 案.xlsx` 时，传前者打开的是**后者**（`[1]` 被当作字符类）。`-FilePath ([WildcardPattern]::Escape($env:PCH_TARGET))` 或改用 `System.Diagnostics.ProcessStartInfo`（`FileName = $env:PCH_TARGET`、`Verb = $env:PCH_VERB`、`UseShellExecute = $true`，`[Diagnostics.Process]::Start`）都打开了正确的文件（已验证）。日文与空格本身没有问题。
  - Excel 的命令行开关 `/r` 才是只读（直接 `EXCEL.EXE /r "<path>"`：标题 `… - Read-Only - Excel`，无 `~$` 文件，他人可写）。Word 没有对应的只读开关。
  - 「选择应用」对话框的原因（推测，未深究）：本机 `.xlsx` / `.docx` 没有 `UserChoice`（只有 `OpenWithList` / `OpenWithProgids`），而 OpenWithList 中有其他应用；资源管理器双击与现有的 `shell.openPath`（「既定のアプリで開く」）走同一 ShellExecute，也会弹出同样的对话框。没有点「始终」验证（会改变需求方的系统设置）。
- `UserChoiceLatest`：**本机存在**，但只在 `.html` / `.htm` / `.pdf` / `.txt` 下（值在子键 `UserChoiceLatest\ProgId` 的 `ProgId`，`UserChoiceLatest` 本身只有 `Hash`）；`.xlsx` / `.docx` 下没有 `UserChoice` 也没有 `UserChoiceLatest`。`.pdf` 的两者**不一致**：`UserChoice` = `ChromePDF`，`UserChoiceLatest\ProgId` = `MSEdgePDF`；系统实际采用的（`AssocQueryString(ASSOCSTR_PROGID)` 与 open 命令）是 `ChromePDF`（= `UserChoice`）。
- 对计划的影响（Task 9，需要控制者 / 需求方确认的部分已标注）：
  1. **启动命令改写**（必须）：不用 `-LiteralPath`；推荐 `ProcessStartInfo` + `UseShellExecute` + `Verb`（无通配符语义），路径与 verb 仍经环境变量传入。doc 10.3 的示例同步修正。
  2. **`New` 保留**：两种文件都是「以该文件为蓝本新建」，「新規作成」按钮成立。
  3. **`readOnly ← OpenAsReadOnly` 不成立（需确认）**：本机 Office 的 `OpenAsReadOnly` 实际以编辑模式打开，显示「読み取り専用」会误导。建议：不再从 `OpenAsReadOnly` 推出 `readOnly`；有 `ViewProtected` 时始终显示「保護ビュー」（只读、经实测）；若要真正的「只读」，只能对 Excel 走 `EXCEL.EXE /r`（超出 `via: 'verb'` 的设计，另议）。计划 Task 9 Step 1 的测试期望（「edit/readOnly/newFromFile 三项且无 protectedView」）随之调整。
  4. **`edit ← Open` 在本机弹出「选择应用」对话框**：与资源管理器双击行为一致，属系统状态而非应用缺陷；记录在 knowledge，面板文案与行为不另做处理（是否需要说明由需求方决定）。
  5. **ProgId 的取法**：维持设计的「`UserChoice` → `HKCR\<ext>` 默认值」，**不读 `UserChoiceLatest`**（本机系统实际采用的是 `UserChoice`）。若以后发现两者不一致导致错误，可改为在检测脚本中调用 `AssocQueryString`（`Add-Type`）——未实施、未测耗时。

### S7 PowerShell 启动 Office 的延迟

- 做法：Node `execFile('powershell.exe', ['-NoProfile', '-NonInteractive', '-Command', …], { windowsHide: true })`，计 PowerShell 进程从启动到退出的时间；另计从调用到 Office 窗口出现的时间（轮询 `MainWindowTitle`）。
- 结果：空命令 `exit 0` 基线 459–532ms（5 次 × 5 轮）；`Start-Process` 一次 787–1006ms（13 次）；`ProcessStartInfo` 写法 1350ms（1 次）。Office 窗口在调用后 3.8–5.7 秒出现（Office 自身启动，含首次的 Copilot 介绍对话框）；「选择应用」对话框约 2 秒出现。
- 对计划的影响：PowerShell 本身约 0.5–1 秒，相对 Office 的数秒启动可以接受，**不需要 koffi**。建议 `system.launch` 在调用开始时给出「起動中」类反馈（toast 或按钮 loading），由 Task 10 实现者决定。检测脚本（每扩展名读注册表）同样约 0.5 秒起，按设计在首次需要时后台执行。

### S9 electron-vite 增加独立浏览器入口

- 做法：在 scratchpad 建最小 electron-vite 项目（`node_modules` 为指向 `apps/desktop/node_modules` 的目录联接），入口 `src/web-assets/markdown/main.ts`（静态 import 一个与渲染端共享的模块，动态 `import()` 一个代替 mermaid 的分块），试两种构建方式，并在独立会话中注册 `pch-asset` 协议、加载外壳页执行脚本，确认生产与开发两种模式下脚本与分块都能加载（视图控制台输出确认）。
- 结果：
  - **方案 A（renderer 追加 input）可用**：`renderer.build.rolldownOptions.input = { index: …/index.html, markdown: …/main.ts }`，`output.entryFileNames` 用函数给 markdown 固定名 `viewer/markdown.js`。electron-vite 6 的 renderer 预设内部用 `rolldownOptions`，并把 `rollupOptions` 设为同一对象；实测写 `rollupOptions` 与 `rolldownOptions` 产物相同。产物：`out/renderer/viewer/markdown.js`，**但与渲染端共享的模块被拆到 `out/renderer/assets/shared-*.js`，动态分块也在 `out/renderer/assets/`**——`pch-asset` 的根只能是整个 `out/renderer`，白名单无法只覆盖查看脚本。
  - **方案 B（单独的 vite 构建）可用且隔离**：`vite build --config vite.markdown.config.*`（`root` = 查看脚本目录、`base: './'`、`outDir` = `out/web-assets/markdown`、`rolldownOptions.input` = `main.ts`、`entryFileNames: '[name].js'`、`chunkFileNames: 'chunks/[name]-[hash].js'`、`target` 取 Electron 的 Chrome 版本）。产物：`out/web-assets/markdown/markdown.js` + `chunks/*.js`，共享模块被内联，动态分块用相对路径 `./chunks/…` 加载。经 `pch-asset://viewer/markdown.js`（根 = `out/web-assets/markdown`）实测脚本与动态分块都执行。
  - **开发模式**（两方案相同，与 input 配置无关）：`pnpm dev` 的 renderer dev server 能以 `/@fs/<查看脚本的绝对路径>` 提供转换后的 `main.ts`，其中的 import 都是根相对路径（`/@fs/…`、依赖预构建为 `/node_modules/.vite/deps/…`）。因此开发模式下 `pch-asset` 处理器把**所有路径**原样代理到 `ELECTRON_RENDERER_URL`（`net.fetch(base + pathname + search)`），外壳页的脚本地址用 `/@fs/<绝对路径>`：实测 `main.ts`、共享模块与动态分块都经代理加载并执行。monorepo 中 `/@fs` 的访问范围默认是工作区根（vite 源码 `searchForWorkspaceRoot` 以 `pnpm-workspace.yaml` 为标志），`apps/desktop/src/web-assets/` 在范围内——按源码推断，未在真实仓库实测。
- 对计划的影响（Task 8）：推荐**方案 B**：`apps/desktop/vite.markdown.config.ts`（文件名由实现者定）+ `build` 脚本改为 `pnpm typecheck && electron-vite build && vite build -c <config>`（viewer 构建放在 electron-vite 之后：electron-vite 只清空它自己的输出目录，`out/web-assets` 不受影响）；`pch-asset` 根目录 = `out/web-assets/markdown`（生产），开发模式代理到 dev server（脚本地址 `/@fs/…`）。`electron-builder.yml` 的 `files` 是排除式，`out/**` 默认打包；新配置文件要加进排除列表。`pnpm dev` 不需要预先构建查看脚本。方案 A 也能工作，但 `pch-asset` 需暴露整个 `out/renderer`，与设计 5.4「只提供查看脚本及其分块（白名单路径）」不符，不推荐。外壳的 CSP 在开发模式下需允许代理来的 `/@fs` 脚本（同为 `pch-asset:` 源，`script-src pch-asset:` 即可；Vite 的 HMR 客户端不会注入到 JS 入口，实测没有请求 `/@vite/client`）。

### setBounds 的单位

- 做法：读 `electron.d.ts` 的 `View.setBounds(bounds: Rectangle, options?: BoundsOptions)`——没有写单位，只有 `Rectangle` 各字段「must be an integer」。实测：宿主页放一个蓝色占位元素（CSS `left 120 / top 80 / 400×300`），外围 1px 品红框；视图背景绿色；`setBounds` 直接用 `getBoundingClientRect()` 的值（不乘 `devicePixelRatio`）。系统截图（物理像素）后统计各颜色的外接矩形。分别在本机原生 150% 与 `--force-device-scale-factor=1.25` 下运行。
- 结果：**单位是 DIP**；宿主页面缩放为 1 时与 CSS 像素一致。
  - 125%：绿色从物理 (150, 100) 开始（= 120×1.25, 80×1.25），高 375（= 300×1.25）；蓝色像素数为 0；品红 1px 框四边完整可见。
  - 150%：绿色从 (180, 120) 开始，高 450；蓝色为 0。
  - 绿色宽度比预期少约 15 CSS px，是视图页面自身的纵向滚动条（截图确认），不是错位。
  - 传小数 `{ x: 120.4, y: 80.6, width: 400.5, height: 300.5 }` 不报错，`getBounds()` 为 `{ 120, 81, 401, 300 }`（Electron 四舍五入）。
- 对计划的影响：Task 6 / 7 的宿主直接发送 `getBoundingClientRect()` 的值，**不乘 `devicePixelRatio`**；在宿主侧自行取整（建议 `x = round(left)`、`width = round(right) - x`，避免相邻元素之间出现 1px 缝），不要依赖 Electron 的隐式取整。宿主页面若被缩放（`webContents.zoomFactor ≠ 1`），CSS 像素 ≠ DIP，需要乘以缩放系数——应用目前没有缩放功能，未验证。设计 5.2 的对应句已按此修正。

## 浏览器视图管理与 IPC（Task 6，2026-11-20）

实验：scratchpad 的 `task6/spike/`（最小 Electron 脚本）与 `task6/verify.mjs`（启动已构建的应用，经 `window.pch.invoke('web.*')` 走真实路径；样本目录 `task6/site/`，含 64MB 的 `big.bin` 与 MediaRecorder 生成的 193MB `big.webm`）。未进产品代码。

### 决定

- **`createView` 的签名**：计划写 `createView: (session) => ViewLike`；实现为 `createView: (events: ViewEvents) => ViewLike`——会话由组合根闭包绑定（`createWebContentsView(webSession, events)`），Electron 事件在真实工厂（`web-session.ts`）中转为 `ViewEvents` 回调，manager 的判定与发送可用假对象单元测试。`OwnerWindow = { id, add(view) }`，`ViewLike` 自带 `destroy()`（从窗口移除并 `webContents.close()`）。

- **CSP**：设计 5.4 的原值，另在 img-src / style-src 追加 `http:`（审查后控制者裁定：本地页面允许访问外网，内网系统常为 http，Markdown 引用的内网图片应能显示；script-src 仍只允许 `pch-asset:`）。审查第 1 轮追加 `frame-src 'none'`、`base-uri 'none'`、`form-action 'none'`：frame-src 原本落到 default-src，Markdown 中 `<iframe src="./x.html">` 加载的同源本地 HTML 没有 CSP，脚本执行并改动了外壳的标题（e2e 在修复前的构建上实测为 `z`）；mermaid 的 strict 模式不用 iframe（修复后 mermaid 图照常生成）。实测 mermaid 12 不需要 `unsafe-eval`；视图控制台只有 Markdown 中 `onerror=` 被阻止的 CSP 报错，mermaid 无任何违规。`<script>` 由 `innerHTML` 插入本就不执行（单元测试只断言它原样保留，按裁定；e2e 用 `onerror=` 改标题的用例证明 CSP 生效——不阻止的话错误事件晚于查看脚本设标题，标题会变为 `y`）。
- **主题（S2）**：`markdown.css` 与 mermaid 主题都看 `prefers-color-scheme`，不带 `&theme=`。主题切换时 mermaid 颜色写死在 SVG 里，查看脚本监听 `matchMedia` 的 `change` 按新主题重新渲染（保持滚动位置；实测节点填充色 `rgb(236, 236, 255)` → `rgb(31, 32, 32)`，背景 `rgb(13, 17, 23)`）。
- **页面标题**：查看脚本设 `document.title` = 第一个 h1，没有时为文件名（否则 Chromium 以 URL 合成标题，状态行显示 `pch-web://…?pch-view=markdown`）。
- **HTML → Markdown 不复用视图**：按 Task 7 的「所有者不同 → release」，从 HTML 页面点 `.md` 链接会销毁旧视图、新建视图（回到 HTML 同样新建，sessionStorage 从头开始）；Markdown 之间（同一插件）复用。e2e 原有的「notes.md → 文本查看器、视图数 0」改为此断言。
- 插件名：ja「Markdown 表示」/ zh-CN「Markdown 显示」/ en「Markdown」。界面与共用文案在审查第 1 轮抽到 `plugins/builtin/src/web-page/`（`WebPagePreview({ view, external? })`、`webPageMessages(name)`），html / markdown 插件只传参数；eslint 新元素 `plugin-web-page`（排在 `plugin` 之前，只依赖 plugin-sdk / ui，`captured: { name: ['html', 'markdown'] }` 的插件才能引用；用临时文件核实 text 插件引用它、它引用 text-engine 或插件都报错）。

### 审查第 1 轮修复（Task 9）：开关方式启动不再挂起

- 问题：开关方式用 `UseShellExecute=$false` 时 .NET Framework 以继承句柄创建进程，Excel 继承了 Node 给 powershell 建的 stdout / stderr 管道，`execFile` 要等 Excel 退出或 15 秒超时才返回（超时还被当作成功）。

- `/r` 重新实测（经 `LauncherService.open(…, 'readOnly')`，`sample [1] 見積.xlsx`）：`open` 在 1569ms 返回；标题 `sample [1] 見積.xlsx - Read-Only - Excel`；同目录无 `~$` 文件 -> 仍然只读。EXCEL 按 PID 结束；结束后 EXCEL / WINWORD / wscript 进程数为 0。

### 视图加载时抢焦点（I3 / Q18）

- 复现（e2e，旧构建）：资源树选中 `app.js` 后按 ↓ 到 `index.html`，视图加载后 `webContents.isFocused()`：应用 false、视图 true。
- 事件顺序（主进程监听，新建视图一次）：`created` → `did-start-loading` → 约 50 ms 后应用 `blur`、视图 `focus` → `dom-ready` → `did-stop-loading`。焦点在加载开始后、文档就绪前被拿走。
- 在视图的 `focus` 事件处理中**同步**调用应用 `webContents.focus()` 不生效（焦点仍在视图，之后没有任何 focus / blur 事件）；推迟到 `setImmediate` 之后调用生效（视图 `blur`、应用 `focus`，之后 `dom-ready` / `did-finish-load` 也不再拿走）。实现据此在 `web-session.ts` 中推迟 `focused()`。
- 修复后 e2e：↓ 经过 `index.html`、`notes.md`（新建 Markdown 视图）后应用持有焦点、资源树仍持有 DOM 焦点；主进程 `sendInputEvent` 点击页面后视图持有焦点（`before-mouse-event` 对 `sendInputEvent` 的鼠标事件同样触发）。

### `runPowerShell` 的超时（Task 9 deferred 核对）

- `execFile` + `timeout: 2000`，脚本以 `UseShellExecute=$false` 启动睡 6 秒的 `wscript.exe` 后立即以 0 退出：2123 ms 回调，`error` 为 null、stdout 为脚本输出。即孙进程持有管道时超时被当作成功；现在的开关 / verb 脚本都用 `UseShellExecute=$true`，不再触发。
