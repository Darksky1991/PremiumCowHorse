### Step 4：读 `node_modules/ssh2` 核实

源码路径：`apps/desktop/node_modules/ssh2/`（版本 1.17.0）。除读 README / `lib/client.js` 外，用一次性脚本（scratchpad，不进仓库）在回环地址起 ssh2 自带的 `Server`，用 `Client` 实测了 hostVerifier / authHandler / keyboard-interactive 三项。

1. **`hostVerifier`**（README.md 第 955 行；`lib/client.js` 第 273–287 行）
   - 签名 `(key[, callback])`。内部实现 `hostVerifier = (key, verify) => { ...; const ret = hashCb(key, verify); if (ret !== undefined) verify(ret) }`：**同步返回 `true/false`，或返回 `undefined` 并在稍后调用 `verify(true|false)`（异步）**，两种形式都可用。
   - 未设置 `hostHash` 时 `key` 是**原始主机公钥 blob（`Buffer`）**；设置 `hostHash`（如 `'sha256'`）时是该哈希的 **hex 字符串**（第 277–283 行）。
   - 实测：`Buffer.isBuffer(key) === true`，且 `key.equals(utils.parseKey(hostPrivateKey).getPublicSSH()) === true`（即 SSH wire 格式的公钥 blob，可交给 `utils.parseKey` 取类型）；异步 100 ms 后 `verify(true)` 握手继续。
   - 注意：回调在源码里恒以两参数调用，所以不能靠 `fn.length` 判断是否异步。未设置 `hostVerifier` 时自动接受任何主机密钥（README 第 955 行），**产品代码必须设置**。
2. **`authHandler(methodsLeft, partialSuccess, callback)`**（README 第 879 行；`lib/client.js` 第 855–1080 行）
   - 首次调用 `methodsLeft` 与 `partialSuccess` 均为 `null`，之后为数组与布尔值。可以 **`return`** 下一种方式（方法名字符串或对象 `{type, username, ...}`），或调用 `callback(...)`；**返回 / 传入 `false` 表示没有更多方法**，ssh2 发出 `error`（`level = 'client-authentication'`，消息 `All configured authentication methods failed`）并 `end()`（第 863–866 行）。
   - 实测：首次返回 `{type:'keyboard-interactive', ...}`；服务器拒绝后第二次调用得到 `left=[]`、`partial=false`，`callback(false)` → `error client-authentication All configured authentication methods failed`。**只在首次返回一个对象、之后返回 false，即「只提交一次」，不会自动重试**。
   - `tryNextAuth` 中若已通过 `callback` 响应（`hasSentAuth`）则忽略返回值（第 1075–1080 行），所以「返回」与「回调」二选一即可。
3. **`keyboard-interactive` 的 `prompt`**（README 第 935–941 行）：在 authHandler 返回的对象里写 `prompt: (name, instructions, instructionsLang, prompts, finish) => {...}`，`prompts` 为 `[{prompt, echo}]`，答案数组交给 `finish`。实测：服务器侧 `prompts` 为 `[{"prompt":"Password: ","echo":false}]`，`finish(['secret'])` 后服务器收到 `['secret']`。服务器可能追问更多问题，须自行计数以守「一次只写一次」。
4. **保活**（README 第 957–959 行；`lib/client.js` 第 133–140、710–735 行）
   - `keepaliveInterval` 单位**毫秒**（`> 0` 才启用，默认 0 即关闭）；`keepaliveCountMax` 为**连续未应答次数**（默认 3，`>= 0`）。
   - 逻辑：每个间隔 `++kacount`，`kacount > keepaliveCountMax` 时 `error.level = 'client-timeout'`、消息 `Keepalive timeout`，随后 `sock.destroy()`。应答到达则 `resetKA` 清零。即**发现静默断线约需 `interval × (countMax + 1)`**（15 秒 × 4 = 60 秒，与计划 Review Focus 2 的「约 1 分钟」一致）。保活在 `USERAUTH_SUCCESS` 之后才开始（第 365–367 行）。
   - **未用冻结的服务器实测**，留给 Task 5 的 freeze 测试（已由 R3 放宽上限）。
5. **`readyTimeout`**（README 第 977 行；`lib/client.js` 第 1112–1119 行）：毫秒，默认 20000，覆盖「握手完成」（含认证，`USERAUTH_SUCCESS` 时清除，第 368 行）；超时 `error.level = 'client-timeout'`、消息 `Timed out while waiting for handshake`，并 `sock.destroy()`。`0` 表示不设超时。其他 level：`client-socket`（第 804 行）、`client-dns`（第 1151 行）、`client-authentication`、`agent`。**保活超时与握手超时的 level 同为 `client-timeout`，需靠 `message` 区分**。
6. **`exec(cmd, { pty }, cb)`**（README 第 989–993 行；`lib/client.js` 第 1231–1233 行）：`pty` 为 `true`（默认设置）或设置对象时先 `reqPty` 再 exec；回调 `(err, stream)`。
7. **`utils.parseKey` 对 `.ppk` 的返回**（README 第 1437 行；`lib/protocol/keyParser.js` 第 1007–1160 行）。**以 ssh2 自带样本 `node_modules/ssh2/test/fixtures/id_rsa.ppk`（PPK v2，`Encryption: none`，ssh-rsa）实测**：
   - 无口令：返回对象 `type = 'ssh-rsa'`，`getPrivatePEM()` 返回字符串；可用于 `privateKey`。
   - **对未加密的 `.ppk` 传入口令（包括 `'wrong'`、`'foobarbaz'`）返回 `Error: PPK private key integrity check failed`**（口令参与 Private-MAC 计算）；传空字符串 `''` 则成功。**即只在 `.ppk` 实际加密（`Encryption: aes256-cbc`）时才传口令**。
   - 解析正则（keyParser.js 第 1010 行）只认 `PuTTY-User-Key-File-2: ssh-(rsa|dss)` 与 `Encryption: aes256-cbc|none`。构造一份 **v3 / `ssh-ed25519`** 头：`parseKey` 返回 `Error: Unsupported key format`。**结论：`.ppk` 仅支持 PPK v2 的 RSA / DSA；v3（PuTTY 0.75+ 的默认格式）与 Ed25519 的 `.ppk` 不支持**，须映射为 `CONN_KEY_INVALID`（D5），并在界面提示「请用 PuTTYgen 转换为 OpenSSH 格式」。
   - 未验证：加密的 PPK v2（`aes256-cbc`）样本（ssh2 的 npm 包中没有，本机也没有 PuTTYgen，也不下载可执行程序），仅按源码判断「口令正确则可解」；真实 PuTTYgen 导出的 v2 文件未验证。
   - 注意：`parseKey` 对 OpenSSH 新格式密钥可能返回**数组**（README 第 1437 行），产品代码取第一个元素；错误以返回 `Error` 对象表示而非抛出。

## 控制者决定

D1–D10 原文抄自计划「控制者决定」一节（2026-11-22）。

- **D1** 扫描进程 ↔ 主进程的远程消息名沿用现有消息的驼峰写法：`remoteOp` / `remoteCancel`（扫描进程 → 主进程）、`remoteResult`（主进程 → 扫描进程）（设计写作 `remote.op` 等）。
- **D2** 进程表轮询用**一个长寿命的轮询通道**：`while :; do ps -eo pid=,ppid=,comm=; echo PCHEND; sleep 0.15; done`，判定后关闭（每次切换身份最多多占 1 个会话，不受 `MaxSessions` 频繁开关影响）。
- **D3** 「测试连接」是用户的明确动作：即使连接处于锁定状态也尝试一次；成功则解除锁定（`auth_state = ok`），失败则写入对应的锁定状态。
- **D4** sftp-server 探测与「能否看到 root 进程」的检查在**第一次使用切换身份时**执行（每条 SSH 连接一次），不使用切换身份的连接不执行命令。
- **D5** 新增错误码 `CONN_KEY_INVALID`：私钥文件读不了 / 格式不支持（含 `.ppk` 不支持时）/ 口令错误。属于本机错误，不连接服务器，**不进入**认证锁定。
- **D6** 编辑连接时 `host` 或 `port` 变化 → 清除已信任的主机密钥（需重新确认）。编辑连接一律解除认证锁定。
- **D7** 远程资源不经 `vfs.sniff`、不打开 `doc.*`：渲染端对非 `file:` 资源不 sniff，`SftpProvider.read` / `createReadStream` 以 `FS_UNSUPPORTED_SCHEME` 拒绝且不连接服务器。
- **D8** 「添加远程文件夹」对话框的默认路径经新通道 `connection.home`（登录用户为 `realpath('.')`，其他身份为 `/`）。
- **D9** 远程目录的「属主」（「无权限」提示用）随列表进入缓存：`RawEntry` / `FileEntry` 增加可选的 `owner`，缓存表 `entries` 加列 `owner`，`CACHE_VERSION` 5 → 6。
- **D10** 主进程访问范围（设计 5.7）的检查放在 IPC handler 与扫描进程远程请求的入口（`RemoteAccess`），不放在 `VfsService`：`entry.add` 校验新条目时需要对尚不是条目的 `sftp:` URI 调用 `vfs.stat`。
