# M2 试用反馈的修改（2026-11-21）

分支 `feat/m2-preview-plugins`（M2 已实现、未合并）。需求方试用后提出 8 项反馈，本文记录各项的做法、决定与验证。

## 需求方的反馈与确认结果

1. 修复焦点问题（M2 最终审查遗留：点击页面内链接 / Alt+←→ 回到网页后，键盘焦点落到应用而不是新页面）。
2. 文件树中的目录，Ctrl+单击在新标签打开目录视图。→ 已是现有行为（`e2e/folder.spec.ts` 覆盖），本轮不改。

   - 单击 / ↑↓ 停留 = 当前标签显示文件信息；双击 / Enter = 当前标签用默认预览器；
   - Ctrl+单击 / 中键 / Ctrl+Enter = 新标签用默认预览器；
   - 当前标签已在显示该文件时，再单击不切回文件信息。
4. Excel（Office）的打开方式检测不必每次都做（会闪一下），每台机器检测一次即可。
5. 通过目录视图进入子文件夹后，资源树没有相应展开。
6. 地址栏与其他元素的分隔不明显。确认结果：路径放进「地址框」（圆角、浅底），导航按钮与查看器按钮留在框外。
7. 地址栏工作区部分的选择按钮放在前面，不用向下箭头。确认结果：lucide `LayersIcon`（层叠）。
8. 工作区一级还可以再向上一级，用来选择 / 管理工作区。确认结果：新增「工作区一览」页面（在标签中显示）作为工作区总览的上一级；前置按钮仍是快速切换菜单，菜单底部加「管理工作区…」进入一览页。

## 1. 点击链接后的焦点

### 做了什么

- 问题链路（先读代码、再用 e2e 复现确认）：用户在页面中点同范围链接（web→web）或在页面中按 Alt+←→ 时，渲染端先 `web.hide`（同一查看器）或 `web.release`（查看器不同，html ↔ md）——主进程把视图持有的焦点交回应用——再 `web.attach` 新页面；attach 时视图没有焦点 → `guardFocus = true` → 新页面加载时拿到的焦点又被交回应用。结果键盘焦点在应用界面，↓ 可能移动资源树而离开页面。e2e 在修复前的构建上复现：点链接后 `{ app: true, views: [false] }`。
- 主进程 `WebViewManager`（`apps/desktop/src/main/modules/web/web-view-manager.ts`）：
  - 新增 `handoffs`（窗口 id → 标签 id）：`hide` / `release` 交回了焦点（`yieldFocus` 为真）时记下。
  - `attach`：先取出并清除本窗口的交接；是同一标签时 `guardFocus = false` 并 `webContents.focus()` 视图（复用的视图或新建的视图都一样）；否则维持原规则（`guardFocus = !视图有焦点`）。
  - 新增 `appInput(ownerId)`：作废该窗口的交接；`disposeWindow` 也作废。
- `web-session.ts` 的 `bindWebViewOwner`：给应用窗口渲染端的 webContents 接 `before-input-event`（`type !== 'keyUp'`）与 `before-mouse-event`（`mouseDown`）→ `manager.appInput(id)`。
- 渲染端、IPC 契约不变。

### 关键决定

- **交接放在主进程、不改契约**：焦点是否在视图中只有主进程知道（`webContents.isFocused()`），hide / release / attach 的先后也已由渲染端的按标签队列保证；放在渲染端需要 hide 返回 yielded、attach 增加参数，两处契约变化，收益相同。
- **记在窗口上、按标签匹配，而不是记在视图上**：html → md 的链接（查看器不同）走 release + 新建视图，记在视图上会随销毁丢失。
- **只给紧接着的一次 attach**：任一标签的 attach 都作废交接。页面中按 Ctrl+Tab 切到另一个网页标签时维持原规则（焦点在应用），不扩大焦点自动进入视图的范围。
- **增加「用户在应用中按键 / 按下鼠标」作废**（偏离任务建议的部分，理由）：只按「同一标签紧接着的 attach」判断时，页面中 Alt+← 回到文本文件 / 目录（非网页，release 之后没有 attach），交接会一直留着；之后用户在应用中按 Alt+→、或在目录列表里按 Enter 打开 html 时，焦点会被拉进视图——正是 I3 要避免的「焦点原本在应用里却被视图抢走」。用户在应用中的按键 / 鼠标按下说明焦点已由用户移到应用，以此作废最直接。只看按下：页面中 Alt+← 交回焦点后，键的抬起会落到应用界面（不能算用户操作）。按键与鼠标只在应用渲染端持有焦点时到达它的 `before-input-event`，视图中的按键不经这里。
- 不用计时窗口（例如「hide 后 N 毫秒内的 attach」）：插件首次懒加载的时长不确定，且不能区分上述非网页的情形。

## 3. 资源树的单击 / 双击 / Ctrl

### 做了什么

- `packages/shared/src/layout`：`tab/open` 增加可选的 `viewer`（新标签以该查看器显示；同 URI 已打开时只激活，不改其查看器），`tab/navigate` 增加可选的 `viewer: string | null`（新位置以该查看器显示，`null` / 省略 = 自动选择；**导航到当前 URI 且指定了 `viewer`（含 `null`）时同一位置换查看器**，与 `tab/viewer` 相同：清除 viewState、不入栈；省略时保留当前查看器，原有行为不变）。换查看器的逻辑抽成 `withViewer`，`tab/viewer` 与之共用。
- `stores/tabs-store.ts`：`openHere(workspaceId, target, { newTab?, viewer? })` 把 `viewer` 传给 `tab/open`（只传字符串）/ `tab/navigate`（`null` 也传）。
- `features/explorer/open-target.ts`：新增纯函数 `openRequest(node, gesture, activeUri)` 与类型 `OpenGesture`（`select` = 单击 / ↑↓ 停留，`activate` = 双击 / Enter，`newTab` = Ctrl+单击 / 中键 / Ctrl+Enter / 菜单）。文件节点：`select` → 当前标签、`FALLBACK_PLUGIN_ID`，激活标签已是该 URI 时返回 null；`activate` → 当前标签、`viewer: null`；`newTab` → 新标签、不指定查看器。非文件节点不指定查看器。
- `features/explorer/explorer-tree.tsx`：`openNode(node, gesture)`，调用时从 tabs-store 读激活标签的 URI（↑↓ 防抖到期时读的是那时的状态）后交给 `openRequest`。单击 → `select`；↑↓ 防抖 → `select`；双击（不可展开的节点）→ `activate`（此前只在设置关闭时打开）；Enter → `activate`；Ctrl+单击 / 中键 / Ctrl+Enter / 菜单 → `newTab`。
- 测试：`layout-reducer.test.ts` 新增 5 条、`tabs-store.test.ts` 1 条、`open-target.test.ts` 新增 `openRequest` 的 10 条；`e2e/tabs.spec.ts` 新增覆盖确认表每一行的用例，并按新行为修改其他 spec 中「单击文件即默认预览」的步骤（见「验证」）。
- 文档：`doc/` 11.1 节类型与 reducer 说明、资源树「打开」一条与新增的「文件节点的查看器」一条、11.2「打开」、8.2 键盘一条、10.6 第 2 条（Office）、测试表。

### 关键决定

- **双击换查看器用 `tab/navigate` 到当前 URI + `viewer: null`，而不是另调 `setViewer`**：双击的第一下单击已经以文件信息打开（进入一条历史），第二下只需同一位置换查看器。`tab/navigate` 到当前 URI 本来就不入栈，加上「指定了 viewer 就换」后，资源树只需一次 `openHere` 调用；也覆盖了设置关闭（单击只选中）时双击打开新位置的情形，不必在资源树里分「已在该位置 → setViewer / 否则 → navigate」两路。省略 `viewer` 时保留当前查看器，地址栏点当前段、目录视图等现有调用不受影响。
- **双击 / Enter 在已显示该文件时也换回默认**（包括用户经查看器菜单选过别的查看器时）：确认表中双击 / Enter 的行为是「查看器为默认」，没有例外；单击才有「已在显示则不动」的例外。
- **`tab/open` 同 URI 已打开时不改查看器**：新标签打开（`newTab`）不指定查看器，只激活已有标签是原有语义；`viewer` 只在真正新建标签时生效（没有标签时的单击会走这里）。
- **「当前标签已在显示」用激活标签的 URI 判断，并在操作发生时读取**：↑↓ 防抖 400ms 到期时标签可能已被别的操作改变，按到期时的状态判断才符合「停留时当前标签已在显示」。
- **非文件节点不指定查看器**：目录单击仍是目录视图（控制者决定：非文件节点行为不变）。目录的 `select` 不做「已在显示则跳过」：原 reducer 对同 URI 导航本来就是空操作。
- **设置 `explorer.singleClickPreview` 关闭时**：单击 / ↑↓ 只选中（不变）；双击 / Enter 以默认查看器打开（控制者决定）。
- 判断逻辑放在 `open-target.ts` 的纯函数中（不依赖 store），资源树组件只负责把事件映射为操作，便于单元测试覆盖确认表。

### 追加（控制者）：「无法预览」只在自动选择时显示

实现者指出：fallback 插件对所有文件都显示「この種類のファイルはプレビューできません。」，单击可预览的文件（.txt / .html / .xlsx）显示文件信息时与事实不符。控制者判断这是本项直接带来的，随本项修改：

- SDK `PreviewHost.tabs.selectedViewer(): string | null`（本标签当前位置用户选定的查看器，自动选择时为 null；调用时读 tabs-store 的最新状态）。宿主 `host.ts` 的 `viewer.selected`，容器 `preview-container.tsx` 从 tabs-store 读取。
- fallback 插件：`selectedViewer()` 为 `FALLBACK_PLUGIN_ID`（资源树单击、查看器菜单选定）时不显示「无法预览」；自动选择到本插件（确实没有预览器）时照旧显示。
- 决定：没有另加「用默认预览器查看」按钮——双击 / Enter 与地址栏的查看器菜单已能切换；二进制等确实没有预览器的文件上，这个按钮按下后仍是文件信息，反而令人困惑。
- 验证：`host.test.ts` 新增 1 条（32 passed）；e2e `tabs.spec.ts`「file nodes …」断言单击后的文件信息不含该句、`text.spec.ts` 二进制文件（自动选择）断言含该句（结果见「验证汇总」）。

## 4. Office 检测结果按机器持久保存

### 做了什么

- 新增迁移 `0005-launch-capabilities`（表 `launch_capabilities(machine, ext, data, detected_at)`，主键 `(machine, ext)`；最初只以 `ext` 为主键，审查后加了机器标识，见本节末尾）与 `schema.ts` 类型。简报写的是 0004，但 0004 已被 `cache-strategy` 占用，故为 0005。
- 新增 `modules/launcher/launch-capabilities.repo.ts`（`get` / `put`（upsert）/ `clear`），读出时用 zod 校验；`LauncherService` 经构造参数注入 repo（组合根 `container.ts` 组装）。流程：内存 → 数据库 → PowerShell 检测；成功检测（含「没有任何方式」）写库，失败不写；`redetect()` 改为异步，清内存与数据库。
- 面板 `office-panel.tsx`：「検出中」延迟 300ms 才显示；检测期间按钮区域占位（`min-h-[4.75rem]`）。
- `fake-run.ts` 增加只在 e2e 下生效的检测计数 `__pchFakeDetects`。

### 关键决定

- zod schema 放在 repo 文件内而非 `packages/shared`：shared 中没有现成的 LaunchCapabilities schema，且只有主进程读取库里的数据；用 `satisfies z.ZodType<LaunchCapabilities>` 保证与类型一致。
- 读出时除结构外还要求行内 `ext` 与主键一致，防止串行数据。
- 数据库读写失败只记警告、退回「重新检测 / 不保存」，不让面板报错（检测结果只是缓存）。
- 保留 generation：检测期间 `redetect()` 的结果既不进内存也不写库。
- 占位高度用固定值（说明行 + 一排按钮的近似高度），不改 SDK。

### 验证

已验证：`launcher.service.test.ts` + `persist.test.ts` + 迁移测试（单元）；`e2e/office.spec.ts` 新增用例（重启后检测次数为 0、再検出后为 1）；typecheck / lint / prettier / build。
未验证：「検出中」延迟与占位高度的外观（没有截图）；检测在 `redetect()` 清库之后才落库的极小竞态窗口（generation 检查与写入之间）。

### 审查后的修改（I1：按机器区分）

- 问题：数据库在 `userData`（`%APPDATA%`，Roaming）下，企业终端的漫游配置文件 / AppData 文件夹重定向会让同一个 `pch.db` 跟着用户到别的机器；表只以 `ext` 为键时，「每台机器检测一次」实际是「每个用户配置文件一次」，会在机器 B 上沿用机器 A 的结果（含 A 的 exe 路径）。
- 修改：迁移 0005 尚未发布（本分支未合并），直接修改：增加 `machine TEXT NOT NULL`，主键改为 `(machine, ext)`（`addPrimaryKeyConstraint('pk_launch_capabilities', …)`，与 0003 的 `index_targets` 相同写法）；`schema.ts` 增加 `machine`。`LaunchCapabilitiesRepo` 构造时传入本机标识，`get` / `put`（upsert 冲突列 `(machine, ext)`）/ `clear` 都只针对本机的行；组合根 `container.ts` 传 `os.hostname()`。`LauncherService` 不变（它只经 repo 存取）。迁移注释、doc 第 10 节与表结构同步修正。
- 决定：
  - **机器标识用 `os.hostname()`**，不读注册表 `MachineGuid`：主机名在企业域内唯一，取得不需要 PowerShell / 注册表访问（启动时不多一次进程）；`MachineGuid` 在克隆镜像的机器上可能相同，并不更可靠。代价：机器改名后重新检测一次（无害）。
  - **其他机器的行保留、不清除**：那是那台机器的结果，用户回到那台机器时仍可用；`redetect()` 只清本机的行。
  - 没有加「switch 方式启动失败时作废保存结果」的保险：按机器区分后，结果只会因本机的 Office 变化而过时，面板上已有「再検出」；启动失败本身已提示 LAUNCH_FAILED。

## 5. 目录视图进入子目录时资源树同步展开

### 复现与根因

- 先写 e2e 复现（临时用例，已删除），在修复前的构建上记录每一步树的行（名称 / 层级 / 展开 / 选中 / 是否在视口内）。初始状态分别为：条目根折叠且从工作区总览进入、条目根已展开且单击树中条目打开、树中双击条目打开、条目在被收起的顶层分组中、嵌套条目（子目录 `設計書` 本身也是条目）。
- 结果：所有情况下「同步」机制都在工作——祖先全部展开、目标行选中且在视口内、焦点留在目录视图（既有 `e2e/tree-sync.spec.ts` 也在修复前通过）。**没有任何一种情况下目标目录本身展开**：进入 `設計書` 后树中 `設計書` 是折叠的，看不到目录视图正在显示的子项。
- **根因**：设计 2.4 的同步只「展开祖先 + 选中目标」，目标目录本身不展开是有意的设计（原 e2e 明确断言 `設計書` 的 `aria-expanded` 为 `false`）。需求方说的「相应展开」指的正是目录本身展开（树显示当前所在目录的内容）；设计与期望不一致，不是定时 / 缓存 / 跳过条件上的缺陷。
- 附带观察（未改动）：嵌套条目时，从父条目的目录视图进入同时是条目的子目录，按「最长前缀」规则定位到顶层的那个条目节点，父条目下的同名目录不展开（设计 2.4 / 8.x 的既有规则）。

### 做了什么

- `features/explorer/reveal.ts`：`settleReveal` 在 sync 找到目标且目标可展开（目录、folder 条目）时调用新的效果 `expand(index)`；文件、locate、找不到目标时不调用。
- `features/explorer/explorer-store.ts`：新增状态 `followed`（工作区 → 跟随展开的目录）与纯函数 / 动作 `followTo`（sync 开始时：收起不是新目标、也不在其祖先链上的跟随展开目录，再按原规则展开祖先链）、`openFollowed`（目标出现后展开它本身；已展开的不动、不记）。`toggle` 把被切换的节点移出 `followed`，`collapseAll` 清空。
- `features/explorer/use-reveal.ts`：sync 请求改用 `followTo`（locate 仍用 `expand`）；`expand` 效果调用 `openFollowed`。`evaluate` 是只创建一次的闭包，工作区 id 与 `openFollowed` 经 `latest` 取最新值。
- 测试：`explorer-store.test.ts`、`reveal.test.ts` 新增用例；`e2e/tree-sync.spec.ts` 改写第一条（条目根折叠）的断言并新增「条目根已展开」的用例。

### 关键决定

- **目录本身展开只用于 sync**：搜索结果的「在树中定位」与标题栏「定位到当前项」（locate）保持只选中目标——那是「告诉我它在哪」，不是「我进入了它」。
- **离开时收起跟随展开的目录**（简报提示的「后退时越展越多」）：只展开不收起时，每进入一层都留下一个展开的目录，后退 / 上一级后树里会残留整条走过的路径。只收起「同步自己展开的目录本身」：祖先链的展开维持原行为（与 locate 一致、不扩大改动范围），用户自己展开 / 折叠过的节点归用户所有，不替用户收起。（审查后修改：本来折叠、由同步展开的祖先也记为跟随展开，见本节末尾。）
- **不改跳过条件**：选中节点的 URI 已是该位置时同步不动。树中单击 / ↑↓ 停留打开目录时正是这种情况，所以「目录单击不展开」（需求 7）不受影响，e2e 断言了这一点。
- 目标已展开（用户展开过，或曾作为祖先展开）时不记为跟随展开，离开时不收起：无法区分是谁展开的，保守地保留。代价：先经地址栏直接进入孙目录、再上一级时，作为祖先展开的中间目录保持展开（与修改前相同）。

#### 全量 e2e 发现的回退与修正（撤回 `releaseFollowed`）

- 现象：控制者在修复后跑全量 e2e，`e2e/tabs.spec.ts`「single click opens in the current tab without expanding; …」第 118 行失败——用户点箭头（`toggleRow`）展开「設計書」后 ↑ 应选中其子项 `v1.txt`，实际「設計書」是收起的。
- 根因（systematic-debugging，加临时断言实测确认后撤回）：不是「用户展开的目录被跟随逻辑收起」，而是**用户点箭头之前「設計書」已经是展开的，箭头把它收起了**。序列：中键打开「設計書」→ 同步展开并记为跟随展开 → Ctrl+单击 README（树先选中 README，同步因「选中项已是该位置」跳过）→ `releaseFollowed` 把「設計書」的跟随记录交给用户，它从此一直展开 → 之后激活 README 标签的同步不再收起它。修改前跳过时记录保留，下一次标签驱动的同步收起「設計書」，测试按这个状态点箭头展开。临时断言 `toggleRow` 前 `aria-expanded` 为 false：实测为 `"true"`。
- 判断：`releaseFollowed` 让每一次树中的选中打开（Ctrl+单击、右键菜单、单击）都把同步展开的目录永久留下，「离开时收起」的规则在常见操作下失效，树越积越多——比审查指出的「之后无关的同步时收起」更糟。
- 修正：删除 `releaseFollowed`（函数、store 动作、`use-reveal.ts` 中的调用），跳过时恢复审查前的行为——什么都不做：不收起（不在用户操作树时挪动行），跟随记录保留，到下一次由标签驱动的同步时收起。场景 2（记录同步新展开的祖先）保留。用户用箭头 / 双击 / → 键展开或折叠的节点由 `toggle` 移出跟随记录（原有行为，没有改动），之后不会被收起。
- 场景 1 的结论：维持审查前的行为，作为已知取舍——树中单击别处后，之前跟随展开的目录在下一次标签驱动的同步时收起（时机可能与用户当时的操作无关）。另两种做法分别有「点击时行移动」「越积越多」的问题。
- 测试：
  - 单元 `explorer-store.test.ts`：删除 `releaseFollowed` 的用例；新增「树中打开别处（同步跳过）不改跟随记录：之后由标签驱动的同步收起它；用户随后用箭头展开的目录归用户所有、不再被收起」，按 tabs.spec 的序列在 store 上重放。说明：bug 在 `use-reveal.ts` 跳过分支多调用了一次 `releaseFollowed`，store 层的用例无法对已删除的调用做 RED；RED 的复现是 e2e（修正前的构建上 `tabs.spec.ts` 该用例失败，见上）。

### 关键决定

- **一览视图放在 `features/workspace`，由 `app/` 经 `PreviewContainer` 的 `renderWorkspaces` 传入**（而不是放进 `features/preview`、也不是在 `app/` 里绕过 PreviewContainer 按 kind 分支）：一览要复用 `workspace-dialogs.tsx` 与 `workspace-flows.ts`，放在 preview 就得复制或把对话框搬到共享层；而 PreviewContainer 仍是「标签内容」的唯一入口，内置视图销毁残留浏览器视图的逻辑（`getWebViews().release`）只写一处——在 `app/` 里直接按 kind 选 `WorkspacesPage` 会让从网页导航到一览时视图得不到释放。这与 `TabsArea.renderContent` 的现有组合方式相同。
- **`workspacesTitle` 作为 `LogicalPathContext` 的必填字段**：一览段与「总览的上一级」都需要本地化名称，必填让所有调用方（地址栏、预览宿主）在编译期补上，不会出现英文兜底；名称从 ctx 取而不用标签标题，语言切换后地址栏立即更新。标签栏同理对一览按当前语言显示标题。
- **`Alt+↑` 焦点在输入框时不是命令**（与 F5 相同，不同于 Alt+←/→）：Windows 的下拉选择中 Alt+↑ / Alt+↓ 开合列表，输入框中也可能有自己的含义；焦点在网页视图中时由主进程转发的按键派发在 window 上，不算输入框，照常生效。
- **目录视图插件的 Alt+↑ 不改**：插件处理后 `preventDefault`，全局处理器在 `onKeyDown` 开头就跳过 `defaultPrevented`（React 的合成事件在根容器上处理，早于 window 上的监听）——这是 F5 在资源树中已在用的机制，选「插件处理时阻止」这一支，不改插件、不改全局逻辑。即便两者都执行，目标都是同一个上一级，`tab/navigate` 到当前 URI 也是空操作。
- **切换后的后退放在 `activate` 成功之后**（`switchAndLeave`）：~~旧工作区那时已不显示，后退不会在界面上闪一下~~（**此说法有误**：`activate` 返回时 `useActiveWorkspace` 的查询尚未更新，旧标签会在界面上短暂退回——审查 I2，e2e 已复现；审查后改为一览卸载后再后退，见本节末尾）；切换失败则不后退（还停在一览，用户可以再试）。`backFrom` 只在标签仍处于一览时后退，避免切换期间标签已被别的操作改变时误退。
- **从一览「新建」并切换成功后也后退**：创建后自动切换同样是「从一览切换到另一个工作区」，规则一致。一览渲染自己的 `NewWorkspaceDialog`（带 `onActivated`），标题栏切换器那一个（ui-store 控制）不变。经地址框按钮的快速切换菜单切换时不后退：控制者的规则只针对一览页中的切换，菜单是全局入口。（审查后改为：从一览页经快速切换菜单 / 标题栏切换器切走时同样后退，见本节末尾。）
- **删除不是当前工作区的工作区时不切换**（`removeWorkspace`）：原流程「先切到默认再删」是为了避免删除当前工作区时主进程落到别的工作区；在一览中删除其他工作区时切到默认毫无必要，还会把用户带离当前工作区。副作用：标题栏切换器的删除对话框打开期间当前工作区被别处切换后，确认时也不再切到默认（目标已不是当前工作区），`e2e/app.spec.ts` 的锁定用例仍通过。
- **当前工作区双击 / Enter = 进入其总览**：控制者只定义了「切换到该工作区」，对当前工作区切换是空操作；像资源管理器双击文件夹进入下一级一样进入总览，键盘用户也能从一览回到下一级（↑ 的反方向）。
- **最近使用时间用 `lastOpenedAt`、条目数不显示**：控制者要求不为此新增 IPC；`workspace.list` 已返回 `lastOpenedAt`，值为 null（从未切换过）时不显示这一行。
- **地址框的样式 `border bg-muted/50`**（而不是纯 `bg-muted`）：ghost 按钮的悬停底色是 `bg-muted`（暗色为 `muted/50`），框若也用 `bg-muted`，框内段的悬停在亮色下完全看不见；半透明底 + 边框让框与地址栏行分得清，悬停仍可分辨（亮色 / 暗色截图确认）。容器是自己的元素，没有改 shadcn 组件。
- 一览项的图标用 Layers，与地址框前置按钮、标签栏一致；工作区总览中分组的标题也用 Layers（既有），两处含义不同，记为顾虑交需求方判断。

### 审查后的修改（I2、快速切换菜单、M2、M3、M4）

**I2 + 快速切换菜单：旧标签的「后退一步」等新工作区真正显示之后再做，且不论从哪里切走**

- 问题：`switchAndLeave` 在 `activate.mutateAsync` 返回后立即 `backFrom`，而界面显示哪个工作区由 `useActiveWorkspace()` 决定，它要等 `workspace.changed` → `invalidateQueries` → 再调用 `workspace.active` 才更新；即使先 `await refetchQueries`，TanStack Query 也用 `setTimeout(0)` 通知观察者，而 zustand 同步通知、React 在微任务中渲染（`knowledge/libraries.md`）。结果旧标签先在界面上退回之前的位置（挂载那个位置的插件 / 浏览器视图、资源树为旧工作区执行 sync），之后才换成新工作区。修改前的构建上 e2e 复现：从总览进入一览后双击另一工作区，MutationObserver 在地址栏 / 标签栏记录到 2 次「Default」（旧标签的总览）。
- 修改：
  - 后退改由**工作区一览自己在卸载清理中执行**（`workspaces-page.tsx` 的 `useEffect` 清理）：一览因切换工作区而卸载时，React 已提交新工作区的界面；清理中用新增的 `data/workspace.ts` 的 `useReadActiveWorkspaceId()`（读查询缓存中 `workspace.active` 的当前值，不订阅、不请求）得到显示中的工作区，交给新的纯函数 `listTabToLeave(byWorkspace, tabId, displayedWorkspaceId)`（`workspace-flows.ts`）判断：标签仍存在、仍是其工作区的激活标签、仍在一览，且显示中的工作区已不是它所属的工作区 → `backFrom(tab.id, WORKSPACES_URI)`（没有后退历史时不变）。
  - 删除 `switchAndLeave` 与 `NewWorkspaceDialog` 的 `onActivated`：一览中双击 / Enter 改为 `activate.mutate(id, { onError })`，一览中新建也只是新建并切换——后退统一由卸载清理负责。
  - 因此**地址框的 Layers 快速切换菜单与标题栏的切换器**（切换，以及标题栏的「新建」）从一览页切走时也后退一步，与一览内切换一致；只有旧工作区的激活标签正显示一览时才后退（只有激活标签的内容挂载，非激活标签上的一览不存在、不会卸载；激活标签不在一览时没有一览可卸载）。
- 决定：
  - **挂在「卸载」上而不是挂在切换的 Promise 上**：「界面已显示新工作区」只有渲染结果能证明；一览正好在那次提交中卸载，卸载清理的时机由 React 保证，不依赖 TanStack Query 与 zustand 的通知顺序（审查建议的「`refetchQueries` 之后再后退」仍有上述 `setTimeout(0)` 的间隙）。
  - **按「显示中的工作区已不是标签所属工作区」判断**，而不是「是否由本页发起切换」：标签内导航离开一览、关闭标签、切到同一工作区的其他标签、错误边界重新挂载时显示中的工作区不变 → 不后退；切换失败时不卸载 → 不后退（与之前「失败不离开」相同）。从哪里切换都适用同一规则，菜单、标题栏、一览不必各自实现。
  - 后退在旧工作区不显示时执行：navigation-store 仍会为旧工作区发出 sync 请求，资源树（已是新工作区）按「不是本工作区的请求」丢弃，旧工作区的树状态不变。
- 验证（已验证）：
  - 单元：`workspace-flows.test.ts` 删除 `switchAndLeave` 的 2 条，新增 `listTabToLeave` 3 条（应后退；显示中的仍是该工作区 / 未知时不后退；非激活标签 / 已不在一览 / 已关闭时不后退）。RED：`listTabToLeave` 未定义 3 failed；GREEN 通过。
  - e2e `address-bar.spec.ts` 新增「switching away from the list page (double-click, Layers menu, title bar) steps the old tab back only after the new workspace is shown; other tabs keep their place」：总览 → 一览后，①一览中双击「別件」、②地址框 Layers 菜单、③标题栏切换器各切走一次，①②期间用 MutationObserver 记录地址栏 / 标签栏中出现过的文字（含随即被替换的中间状态），断言从未出现「Default」；每次切回后原标签在总览；④一览标签不是激活标签（Ctrl+单击树中条目开了新标签）时切走再切回，两个标签都不动。修改前的构建上 RED（①处记录到 2 次「Default」）；修改后的结果见下面的汇总。

**M2：网页视图中的 Alt+↑ 不区分页面内的输入框——保持现状并写明**

- 结论：主进程无法可靠判断页面焦点是否在可编辑元素，保持「网页视图中 Alt+↑ 总是上一级」（与 Alt+← / Alt+→、F5 相同）。理由：`before-input-event` 必须在回调中同步决定是否 `preventDefault`；`Electron.Input` 只有按键与修饰键，`WebContents`（含 `focusedFrame`）没有「焦点元素 / 是否可编辑」的同步 API（已查 Electron 45.3.3 的 `electron.d.ts`：`isEditable` 只出现在 `context-menu` 的参数中）；要知道就得 `executeJavaScript` 向页面执行脚本（异步，且等于注入脚本），视图没有 preload，安全约束不变。本地 HTML 中的表单很少，影响有限。
- 修改：只改注释与文档——`modules/web/shortcuts.ts`、`features/address-bar/commands.ts` 的注释，doc 12.2 节 `Alt+↑` 一条与 15 节的转发说明写明「页面中的 `<select>` / `<textarea>` 里也作为上一级」及理由。没有行为变化，没有新测试。

**M3：一览中删除当前工作区——补 e2e**

- 体验上的问题保留：确认后先切到默认工作区，一览（连同确认框）随切换卸载，「削除中」与关闭动画看不到，删除失败时只有提示。可选做法（在一览中删除当前工作区时改用标题栏切换器那一个常驻的确认框、或不在一览中提供删除当前工作区）属于交互取舍，交需求方判断，本轮不改。

**M4：`removeWorkspace` 的 `activeId` 为 undefined**

- 修改：`activeId === undefined`（`workspace.active` 查询出错 / 尚无数据）时按「是当前工作区」处理，先切到默认工作区再删除——无法排除目标就是当前工作区；目标确实不是当前工作区时多一次切换，无害。
