## 2. 待确认的决定清单

每条格式：决定内容 → 当前实现 → 出处。勾选表示「同意当前实现」；不同意的在条目后写意见。编号 R 沿用实现记录的 Ruling 编号。

### 2.1 需要需求方判断

- [ ] **D1 手动快照是否不计入 3 个（Ruling 18）** → 现在按原话「超过 3 个删除最旧的」：每天开机、退出保存一次时，手动快照在第 3 天开机时被删掉。可选：手动快照不计入（另设上限）、或先删旧登录的自动 / 退出快照。出处：34 §9。
- [ ] **D2 Eclipse 实机验证的版本** → 本机没有 Eclipse，验证需下载官方 zip 版，下载前需确认版本（CLAUDE.md 环境约束）。也可以先不验证。出处：34 §5 第 3 条、§6.2。
- [ ] **D3 删除设置键 `session.restoreOnStartup` / `window.onDetachedClose`** → 原 M3 设想的键，现在没有代码读取；建议在「多窗口与会话」确定不做时删除，保留期间无害。出处：34 §5 第 1 条。
- [ ] **D4 「删除」删的是全部快照（Ruling 21）** → 恢复后确认删除时删全部快照，并立即重新记录当前桌面；另一种做法是只删刚恢复的那一份。出处：35 §3。

### 2.2 控制者的决定（影响使用，建议一次确认）

- [ ] **R19 完整读取兜底也改为 60 秒**（原 5 分钟）→ 每分钟对开着窗口的类别各启动一次 PowerShell（约数百毫秒 CPU）；觉得卡可改回。出处：35 §3。
- [ ] **R20 窗口枚举 2 秒、防抖 1 秒**（需求方原定 5 秒，第 2 轮要求「看哪里还能缩短」）。出处：35 §3。
- [ ] **R22 有项目没恢复成功时也允许删除快照**，只提示「保留可以再试」（取代 Ruling 14 的自动判断）。出处：35 §3。
- [ ] **R23 只有多标签窗口加虚线框**；窗口框不提供「全选该窗口」。出处：35 §3。
- [ ] **R24 项目数按标签计**（侧栏、列表、页面、提示一致）；旧快照的项目数随之按标签重算。出处：35 §3。
- [ ] **R12 / R15 每次登录只占 1 个名额** → 自动快照每次登录一份、原地更新；「保存して終了」把它原地改为退出快照；「保存しないで終了」删除它。同一登录内重启本应用时，接回上次退出时的那份继续更新（那次退出时的勾选不再单独保留）。出处：34 §4、§8.2 I2、§9。
- [ ] **R10 退出对话框显示后一直等待回答**（显示前 10 秒内没确认才自动全部保存退出）→ 渲染端卡死在显示之后时窗口关不掉（可用任务管理器）。出处：34 §4。
- [ ] **R17 从快照页恢复并确认删除后，该标签改为「現在」页**。出处：34 §8.2 I6、35 §2.2。
- [ ] **R2 资源管理器窗口内换文件夹后，新旧两项在 1 分钟内同时出现在现场与快照中**（延迟移除的本意，恢复时可不勾）。出处：34 §4。
- [ ] **R8 不记录最小化窗口的正确位置**（窗口位置恢复是非目标，只有 VS Code 退回状态文件中的位置）。出处：34 §4。
- [ ] **R9 资源管理器多标签恢复交给一段固定脚本**，失败时把未恢复的标签逐个开成独立窗口。出处：34 §4。
- [ ] **补充：会话结束（关机通知）时冻结 5 分钟**；**快照按机器（主机名）区分**，改主机名后旧快照不再显示。出处：34 §4。
- [ ] **M2 未就绪时选「保存しないで終了」照常记为不提示**（用户明确选择）。出处：34 §8.2 M2。

### 2.3 已确认（供参考）

- 2026-11-21：M3 改为桌面记录；对象为资源管理器（含标签）/ Office 三件套 / VS Code / Eclipse（官方版），其余程序以后；监控方式；定时 + 手动 + 退出时保存，退出与恢复时可挑选，不按工作区区分；不做自启与托盘；界面方案 2（活动栏入口 + 快照页 + 两个对话框）；云端 Office 文件跳过；窗口关掉 1 分钟后才移除、扫描 5 秒（后由第 2 轮缩短，R20）。
- 2026-11-22 第 1 轮：按软件分组、卡片式、分组不可选；快照最多 3 个、超过删最旧的；恢复后清空并重新扫描（「清空」已由第 2 轮改为确认后删除）。
- 2026-11-22 第 2 轮：自动保存 1 分钟、尽量实时；恢复后删除要确认、不默认删除；卡片等高；资源管理器标签分开显示与选择（退出时同样），能看出哪些在同一窗口。
- 2026-11-22：多个 VS Code 窗口能记录，需求方确认没问题。

## 4. 已知问题 / 待解决

### 4.1 用户可见

- **K1 标签头标题不更新**：快照改名后、切换界面语言后，已打开的快照页 / 「現在」标签仍显示打开时的标题。出处：34 §7 Task 11 / 13。建议 beta 前修。
- **K2 刚启动的程序可能一直不被记录**：`OpenProcess` 瞬时失败的空结果被缓存，该进程的窗口之后一直判为不属于任何一类。出处：34 §8.3 Task 5。建议 beta 前修。
- **K3 资源管理器多标签恢复的重复窗口**：15 秒内未检测到新窗口时按失败处理并逐个补开——冷启动很慢或「在新标签中打开」设置下可能重复（与 V5 同源）。出处：34 §8.3 Task 9。
- **K4 第一次完整读取一直失败时，退出对话框的「保存して終了」一直不能点**（N1）。出处：34 §9。
- **K5 同一登录内重启后，第一次写入的自动快照会沿用上次退出快照上用户起的名字**（N2）。出处：34 §9。
- **K6 保存后清理失败时整个保存报错**（快照其实已写入）。出处：34 §8.3 Task 12b。
- **K7 部分标签恢复时的「已开着」规则**：选中的第一个标签已开着就跳过整个窗口（其余选中的标签也不打开）。出处：35 §2.4。
- **K8 VS Code 标题匹配的限制**：改过 `window.title`、非英文界面的 `(Workspace)`、未打开文件夹的窗口与同名文件、同名不同路径的文件夹只出一项。出处：34 §7 Task 7、knowledge/windows-and-tooling.md。
- **K9 VS Code 在已有窗口中用「Open Folder」换文件夹**：VS Code 只在新窗口打开时写状态文件，换文件夹后若它没有写，该窗口可能暂不被记录，直到下次有新窗口打开（推断，未验证）。出处：本次会话对多个 VS Code 的核对。
- **K10 Explorer 的特殊位置只显示「特殊位置」**，不区分「此电脑」「回收站」等。出处：35 §2.4。
