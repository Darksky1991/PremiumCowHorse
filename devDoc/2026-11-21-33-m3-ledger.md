## Step 1：Office 多实例

**做了什么**

- 用 Excel / Word / PowerPoint 自动化在样例目录生成 `book-a.xlsx`、`book-b.xlsx`、`doc-a.docx`、`pres-a.pptx`（启动前本机没有 Office 进程）。
- 启动：`EXCEL.EXE /x book-a.xlsx`、`EXCEL.EXE /x /r book-b.xlsx`（只读）、`WINWORD.EXE doc-a.docx`、`POWERPNT.EXE pres-a.pptx`，共 4 个进程（两个 Excel 进程各一个）。
- 脚本 `office-spike.ps1`：`EnumWindows` 取可见顶层窗口（`XLMAIN` / `OpusApp` / `PPTFrameClass`，按 pid 过滤），`AccessibleObjectFromWindow(hwnd, OBJID_NATIVEOM = 0xFFFFFFF0, IID_IDispatch)` 取对象，再取 `Application` 并枚举 `Workbooks` / `Documents` / `Presentations` 的 `FullName`、`ReadOnly`。

**实测输出摘录**（路径缩写为 `...\spikes\`）

```json
{"pid":30508,"class":"XLMAIN","hwnd":789658,"topNativeOM":false,"src":"child:EXCEL7","app":"Excel","version":"16.0","ms":8,"error":"","items":[{"fullName":"...\\spikes\\book-a.xlsx","readOnly":false}]}
{"pid":31632,"class":"XLMAIN","hwnd":396986,"topNativeOM":false,"src":"child:EXCEL7","app":"Excel","version":"16.0","ms":212,"error":"","items":[{"fullName":"...\\spikes\\book-b.xlsx","readOnly":true}]}
{"pid":26764,"class":"OpusApp","hwnd":135038,"topNativeOM":false,"src":"child:_WwG","app":"Word","version":"16.0","ms":366,"error":"","items":[{"fullName":"...\\spikes\\doc-a.docx","readOnly":false}]}
{"pid":29292,"class":"PPTFrameClass","hwnd":69518,"topNativeOM":false,"src":"child:mdiClass","app":"PowerPoint","version":"16.0","ms":81,"error":"","items":[{"fullName":"...\\spikes\\pres-a.pptx","readOnly":false}]}
```

**发现**

1. **顶层窗口上取 `OBJID_NATIVEOM` 失败**（`topNativeOM:false`，返回非零 HRESULT）。要对**子窗口**取：Excel 取类名 `EXCEL7`、Word 取 `_WwG`、PowerPoint 取 `mdiClass`，得到 Window 对象，再 `.Application`。两个 Excel 进程各自取到自己的 Application（`GetActiveObject` 只能拿到一个，此法可逐进程取）。
2. 每个 Excel 进程还有不可见的 `XLMAIN` 窗口（取不到对象）：只处理 `IsWindowVisible` 的窗口；同一 pid 可能有多个顶层窗口（Excel 每个工作簿一个窗口），按 pid 去重，经 `Application.Workbooks` 枚举全部文档。**本次每个进程只开了一个文档，同一进程多文档未实测**。
3. 在 PowerShell 里用原生属性访问（`$app.Workbooks.Item(1).FullName`）可用；用 `[System.__ComObject].InvokeMember(..., 'Count')` 会报 `DISP_E_UNKNOWNNAME`，不要用。
4. **Word 的 `Documents.Item(i)` 要传 `[ref]`**（`$col.Item([ref]$i)`），Excel / PowerPoint 直接传整数。
5. PowerPoint 的 `ReadOnly` 是 MsoTriState（0 / -1），转 `[bool]` 即可。
6. 耗时：各应用单次取一组文档 8 ~ 366 ms（含首次 COM 绑定）；整个脚本（4 窗口，含启动 PowerShell）约 1.7 秒。

**弹出对话框时的行为**

- 本次测试中 Word 与 PowerPoint 启动后自发弹出了 Copilot 的介绍模态对话框（`NUIDialog`）。**Word 在此状态下所有自动化调用立刻被拒绝**（`RPC_E_CALL_REJECTED 0x80010001`）。PowerShell 的原生属性访问会**静默返回 `null`** 而不抛错（`fullName: null`），所以脚本必须把「`FullName` 为空」当作失败；关掉对话框后恢复正常（366 ms）。
- 手动按 F12 弹出「另存为」（`#32770`）后重复：
  - Excel：对 `EXCEL7` 取对象在 24 ms 内返回失败（`no Application`），不阻塞；另一个 Excel 进程不受影响。
  - Word：146 ms 返回，`FullName` 为 `null`（被拒绝），不阻塞。
  - PowerPoint：「另存为」与 Copilot 介绍对话框打开时，仍能取到文档信息（81 ~ 143 ms）。
- 在实际测过的对话框状态下（Excel / Word 的 F12「另存为」、Word 与 PowerPoint 的 Copilot 介绍框）**都没有出现阻塞或卡住**，都是毫秒级返回失败 / 空（单次观察；未测 PowerPoint 的「另存为」及其他对话框）。设计 5.2 的「每次读取 10 秒超时、超时保留上一轮结果」仍作为兜底保留，但主要失败形态是「立即失败 / 返回空」，**失败 = 保留该类上一轮结果**。

**结论：部分验证。** 限定：只验证了每个进程一个文档，同进程多文档、无路径文档未实测；对话框场景为 Excel / Word 手动 F12（另存为），PowerPoint 只验证了 Copilot 介绍框、未验证另存为；「不阻塞而返回 null / 失败」均为单次观察。产出：Task 6 取法为「枚举可见 `XLMAIN` / `OpusApp` / `PPTFrameClass` 顶层窗口 → 对子窗口（`EXCEL7` / `_WwG` / `mdiClass`）`AccessibleObjectFromWindow(OBJID_NATIVEOM)` → `.Application` → 枚举集合」，按 pid 去重，空值 / 异常视为失败。输出 JSON 样例：

```json
[
  {
    "pid": 30508,
    "app": "excel",
    "items": [{ "path": "C:\\...\\book-a.xlsx", "readOnly": false }]
  },
  { "pid": 31632, "app": "excel", "items": [{ "path": "C:\\...\\book-b.xlsx", "readOnly": true }] },
  { "pid": 26764, "app": "word", "items": [{ "path": "C:\\...\\doc-a.docx", "readOnly": false }] },
  {
    "pid": 29292,
    "app": "powerpoint",
    "items": [{ "path": "C:\\...\\pres-a.pptx", "readOnly": false }]
  }
]
```

## Step 2：资源管理器

**做了什么**：脚本 `explorer-spike.ps1`、`explorer-clsid.ps1`。用 `explorer.exe C:\Windows` 开一个测试窗口（按「启动前已有 hwnd」之差识别），UI Automation 找 `AutomationId = AddButton` 并 `Invoke`，再对新出现的 `Shell.Application` 项调用 `Navigate2`。运行时本机没有其他资源管理器窗口。

**实测输出摘录**

```
AddButton found: True
new tab item appeared after 414 ms; items=2; newPath=::{F874310E-B6B7-47DC-BC84-B9E6B38F5903}
-- after Navigate2('C:\Windows\System32'):
item: C:\Windows

tab: System32
Navigate2('shell:::{645FF040-5081-101B-9F08-00AA002F954E}') OK -> ::{645FF040-5081-101B-9F08-00AA002F954E}

Navigate2('::{645FF040-5081-101B-9F08-00AA002F954E}')         FAIL: Value does not fall within the expected range.
Navigate2('shell:::{20D04FE0-3AEA-1069-A2D8-08002B30309D}')   OK -> ::{20D04FE0-3AEA-1069-A2D8-08002B30309D}

```

**发现**

1. `AddButton` 点击后约 400 ms 内 `Shell.Application.Windows()` 出现同 `HWND` 的新项（新标签的初始位置是「主文件夹」页 `::{F874310E-B6B7-47DC-BC84-B9E6B38F5903}`）；对该项 `Navigate2('C:\Windows\System32')` 成功，新标签带到指定路径，`TabItem` 顺序与项顺序一致（`Windows`、`System32`）。新标签对应的项用「点击前已知的项之外的那一个」识别（`ReferenceEquals` 比较 COM 对象可行）。
2. 特殊位置（`::{CLSID}`）：**`Navigate2` 必须传 `shell:::{CLSID}`（或 `shell:RecycleBinFolder` 之类的 shell 名），不能传裸 `::{CLSID}`**（报 `ArgumentException`）。采集到的路径是 `::{CLSID}` 形式，恢复时要加 `shell:` 前缀。`explorer.exe shell:::{CLSID}` 开新窗口也可行（第一个标签用它或 `Navigate2` 均可）。
3. UI Automation 的 `TabItem` 会包含「主文件夹」页内的子标签（日文界面下显示为「お気に入り」「最近使った」等，本次输出因代码页乱码），与讨论时结论一致，需过滤。
4. **关闭测试窗口**：计划写的「逐个标签 `Quit()` 后再 `WM_CLOSE`」**在一次观察中关不掉含 3 个以上标签的窗口**（连续 5 轮 `Quit()` + `WM_CLOSE`，窗口仍在）。另一个测试窗口则在多轮 `Quit()` + `WM_CLOSE` 后被关闭，两次结果不一致，原因未查清。一次观察中可用的方法（单次验证）：用 UI Automation 找 `AutomationId = CloseButton` 并 `Invoke`，**一次点击整个窗口关闭**（脚本 `explorer-closetabs.ps1`）。两个测试窗口都已关闭，本机恢复为无资源管理器窗口。

**结论：部分验证。** 限定：「`Quit()` + `WM_CLOSE` 关不掉 3 个以上标签的窗口」与「`CloseButton` `Invoke` 一次关闭整窗」各只有一次观察，第一个测试窗口如何被关闭未查清；`CloseButton` 只是推荐做法（单次验证），不是已充分验证的标准做法，夹具须在 finally 中确认窗口消失。产出：Task 9 标签恢复 = 第一个标签 `explorer.exe <路径>` 开窗口（取该窗口 hwnd，用启动前后差集识别）→ 对后续每个标签：`AddButton` `Invoke` → 等新项出现（每 100 ms 轮询，最多约 4 秒）→ `Navigate2(路径 | 'shell:' + '::{CLSID}')`。做不到时按设计退回每标签一个窗口。

## Step 3：VS Code

**做了什么**：脚本 `vscode-spike.ps1`、`vscode-titles.ps1`、`vscode-close.ps1`。`Code.exe -n <folder-a>` 与 `Code.exe -n <ws-b.code-workspace>`（以及第二轮 `folder-b` + 同一 workspace），每 0.5 ~ 5 秒轮询 `storage.json` 的修改时间；窗口关闭只对新窗口 hwnd 发 `WM_CLOSE`；`storage.json` 只读。需求方已有的 VS Code 窗口未动。

**实测输出摘录**

```
[before]  mtime=20:09:35  opened=0  (只有 lastActiveWindow = PremiumCowHorse 文件夹)
launch 21:47:15 / 21:47:19  -> storage.json mtime=21:47:24.866, opened=3 （之后 60 秒内没有再写）
close 两个新窗口 -> 30 秒内 mtime 不变，openedWindows 仍列着已关闭的窗口
第二轮 launch 21:49:36 -> mtime=21:49:40.147，openedWindows 变为 当前开着的 3 个（folder-a 消失，folder-b 出现）
窗口标题：'folder-b - Visual Studio Code'、'ws-b (Workspace) - Visual Studio Code'
```

`windowsState` 字段（本机 VS Code 版本）：

- 文件夹窗口：`folder`（`file:///c%3A/Users/.../folder-a`，URI 编码）、`backupPath`、`uiState{mode,x,y,width,height,alwaysOnTop}`。
- workspace 窗口：**`workspaceIdentifier: { id, configURIPath }`**（`configURIPath` 为 `file:///c%3A/.../ws-b.code-workspace`），**不是计划里写的 `workspace.configPath`**；同样有 `backupPath`、`uiState`。
- `lastActiveWindow` 与 `openedWindows` 中的项同结构；`remoteAuthority` 本次没有出现（无远程窗口）。
- `uiState.x/y` 在本机显示器配置下可能是 0 / 0（新窗口）；只读字段，不能当作窗口真实位置，位置以 `GetWindowRect` 为准（设计里窗口位置已由 koffi 提供）。

**发现**

1. **写入时机**：新窗口**打开后约 4 ~ 9 秒写一次**，写入的是「那一刻开着的窗口集合」；**关闭窗口不会触发写入**（关闭后至少 30 秒内不变，已关闭的窗口仍留在 `openedWindows`）。下一次打开窗口时才刷新。因此 `storage.json` 不能表示「现在开着什么」，只能作为「文件夹名 → 路径 / workspace」的查找表。
2. 窗口标题只有文件夹名（`folder-b - Visual Studio Code`）或 `<名> (Workspace) - Visual Studio Code`，与状态文件的对应方法：窗口标题去掉后缀后，与 `openedWindows` 条目的文件夹最后一段 / workspace 文件名（去掉 `.code-workspace`）匹配；重名时无法区分（记为「无法确定」并跳过，或同名全部保留）。**只保留与当前 Code 可见窗口数相符、且名称能对上标题的条目**，计划 Task 7 已按此意思写，字段名要改。
3. 窗口刚启动时标题是 `Visual Studio Code`（还没有文件夹名），约数秒后才变成带名字的标题；监控的防抖要覆盖。
4. 全局 `state.vscdb`（`?immutable=1` 只读，`node:sqlite` 可打开）的 `ItemTable` 中**没有** `history.recentlyOpenedPathsList` 等「最近列表」键（只有终端历史、设置搜索历史等），所以计划里的备用方案（用 `state.vscdb` 最近列表匹配）在本机版本上不可用；`storage.json` 的 `windowsState` + 标题匹配是唯一来源。

**副作用（如实登记）**：`Code.exe -n` 打开测试文件夹 / workspace 会让 VS Code 自己更新 `storage.json`（`windowsState`）（本应用与脚本没有写入，storage.json 全程只读），验证因此改动了需求方 VS Code 的 `storage.json`（`openedWindows` 中出现过 `folder-a` / `folder-b` / `ws-b` 的条目，之后会被 VS Code 自己的写入刷新）。是否同时改动了「最近打开列表」未核实（`state.vscdb` 中没有该键，见发现 4）。

**结论：已验证。** 产出：Task 7 取法 = 窗口标题（`Code.exe` 的 `Chrome_WidgetWin_1` 可见窗口）+ `storage.json` 的 `windowsState.openedWindows`（`folder` / `workspaceIdentifier.configURIPath` / `remoteAuthority` / `uiState`），以标题匹配；字段名按本表。恢复用 `Code.exe <文件夹>` / `Code.exe <workspace 文件>`（本次用 `-n` 打开均成功）。

## Step 4：登录时刻

**做了什么**：脚本 `koffi-spike.cjs`。koffi 调 `wtsapi32.WTSQuerySessionInformationW(NULL, 0xFFFFFFFF /* WTS_CURRENT_SESSION */, 24 /* WTSSessionInfo */, &buf, &len)`，用 `koffi.decode` 按 `WTSINFOW` 结构读，再 `WTSFreeMemory`。同时测退路：`GetShellWindow` → pid → `GetProcessTimes`。分别在 Node 26 和 `ELECTRON_RUN_AS_NODE=1` 的 Electron 45.3.3 下运行。

**实测输出摘录**

```
WTS result: {"bytes":216,"sizeof":216,"sessionId":1,"state":0,"logon":"2026-11-21T09:07:29.759Z","connect":"2026-11-21T09:07:22.805Z","current":"2026-11-21T12:52:35.220Z","user":"yongjun.fu"}
shell pid 16024 created 2026-11-21T09:07:39.181Z
对照：Win32_LogonSession（LogonType 2）StartTime = 2026-11-21T09:07:29.424Z；LastBootUpTime = 09:07:11Z
```

**发现**

1. `LogonTime` 取得成功，与 `Win32_LogonSession` 的开始时刻相差 0.3 秒（09:07:29.759 vs 09:07:29.424），`CurrentTime` 与当前时刻相差 2 ms，`state = 0`（WTSActive）。返回字节数等于 `koffi.sizeof(WTSINFOW)`（216）。
2. **`WTSINFOW` 的字段长度**：`WinStationName[32]`、`Domain[17]`、`UserName[21]`（均 UTF-16）；第一次按 33 / 18 / 21 声明时 `UserName` 错位 2 个字符（读出 `ngjun.fu`），`LogonTime` 的偏移因 8 字节对齐而不受影响。最终声明已用 `UserName = yongjun.fu` 验证。
3. 退路（shell 进程创建时刻）可用，比登录时刻晚约 10 秒；只作为 WTS 失败时的退路。
4. **未验证**：注销再登录后 `LogonTime` 是否变化（需要注销需求方正在使用的会话，本次不做）。会话 ID 与 `LogonTime` 的语义按 WTS 文档，留给 Task 10 的真实重启观察。

**结论：已验证（取得方式）；注销再登录后的变化未验证。** 产出：Task 5 `getLogonTime` = 上述 WTS 调用；结构体声明如 `koffi-spike.cjs`；失败时退回 shell 进程创建时刻。FILETIME → 毫秒：`Number(BigInt(ft) / 10000n - 11644473600000n)`。

## Step 5：koffi 枚举耗时

**做了什么**：`koffi-spike.cjs` 中，`EnumWindows`（`koffi.register` 回调）枚举，对每个可见且有标题的窗口取标题（`GetWindowTextW`）、pid、进程路径（`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageNameW` + `CloseHandle`）、矩形（`GetWindowRect`）；预热一次后测 100 次。在 Electron 45.3.3（`ELECTRON_RUN_AS_NODE=1`，最接近主进程）与 Node 26 下各一轮。

**实测输出摘录（Electron 45.3.3）**

```
no-cache  all-visible-titled: windows=47 median=1.93ms p95=3.31ms max=5.24ms min=1.77ms
no-cache  targets-only      : windows=2  median=1.87ms p95=2.53ms max=3.09ms min=1.73ms
pid-cache all-visible-titled: windows=47 median=0.22ms p95=0.44ms max=0.94ms min=0.18ms
pid-cache targets-only      : windows=2  median=0.19ms p95=0.48ms max=1.24ms min=0.15ms
```

Node 26：no-cache 中位数 1.63 ms / 最大 2.35 ms；pid-cache 中位数 0.19 ms / 最大 0.43 ms。

**发现**：中位数达标（< 5 ms），最大值未全部达标：无缓存时中位数约 1.6 ~ 1.9 ms，最大值偶尔触到 5.2 ms（Electron 下一轮样本中一次）；对 pid → 进程路径做缓存后中位数约 0.2 ms、最大约 1 ms。每 5 秒一次的开销预计可忽略，主进程内耗时待 Task 5 实现后复测。建议 Task 5 对 pid → 路径做缓存（pid 复用风险：缓存项带进程创建时刻或在窗口集合变化时校验）。注意本测试在「无其他重负载」条件下，且不是真正的 Electron 主进程（`ELECTRON_RUN_AS_NODE`）。
