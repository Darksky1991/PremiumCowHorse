# M4 远程目录（SFTP 只读）：设计

- 日期：2026-11-22
- 状态：**已批准（需求方，2026-11-22）**（标注「需求方」的各条已在讨论中确认；标注「控制者」的是控制者的决定，随定稿一并认可）
- 位置：M3 合并之后（`main` @ `eb0875d`），分支待建 `feat/m4-sftp`
- 取代：`doc/` 路线图 M4 行（「连接管理界面、safeStorage、SMB/FTP/SFTP Provider、连接池、远程缓存、主机密钥确认、连接状态显示；FTP/SFTP 上 Office 文件的远程编辑会话与冲突处理」）。需求方 2026-11-22：**放弃 SMB**（「意义不是很大」）；M4 只做 **SFTP 只读**；FTP、Office 远程编辑会话、远程文件缓存（下载）移到「后续」

## 1. 目的与背景

对应产品目标（memory「product goals」）：1「文件和目录散落各处，只整理自己关心的目录并直接浏览」、2「集中查看」、3「按案件隔离」。对日运维的日常是登录客户的 Linux 服务器看目录和日志；现在这些目录只能在终端或 WinSCP 里看，无法与本地目录放在同一个工作区里。

需求方描述的账号结构（2026-11-22）：

- **公司场景**：每人一个个人账号（`user`），维护的每个系统一个系统账号（`app1`、`app2`…），`user` 被授予 sudo 权限，平时用 **`sudo su - app1`** 切换，**要输密码**。
- **个人场景**：root 与个人账号两种就够了。
- 发行版至少考虑 **RHEL、Ubuntu、SUSE、Debian**。

## 2. 目标、非目标、反目标

### 目标

1. **连接管理**（需求方）：活动栏「远程连接」视图**只用于远程设定**（新建 / 编辑 / 删除 / 测试连接），不在这里显示文件树。
2. **远程目录作为条目加到资源管理器**（需求方）：文件树仍在资源管理器中，与本地目录一样参与分组、拖放、标签、搜索。
3. **身份切换**（需求方）：登录用户之外，可以「以 app1 / root 身份」浏览。实现方式见第 5.4 节（已在 4 个发行版上实测）。
4. **缓存**（需求方）：与 Windows 本地不同，**只在选中目录或展开目录时读取并缓存**；**定期扫描只对明确设为「建立索引」的目录**进行。
5. **文件只显示兜底的文件信息**（需求方）：不做文本 / 日志预览，不下载、不用系统应用打开。
6. **保活与超时重连**（需求方提出）：第 5.3 节。
7. **只读**：不向服务器写入任何东西（项目原则「应用不变动文件和目录的数据」）。

### 非目标（本次不做，记录）

- SMB（需求方放弃）、FTP / FTPS、Office 远程编辑会话（doc 10.5）、远程文件的下载缓存（doc 7.4）、文本 / 日志 / Markdown / HTML 等预览（需求方）。
- 堡垒机（踏み台）/ ProxyJump（需求方 2026-11-22：暂不需要）。
- ssh-agent / Pageant、证书认证、Kerberos / GSSAPI（控制者：以后按需）。
- `sudo su` 以外的切换方式（`sudo -u`、`sudo -i`、`su` 直接切换、`pbrun` 等）（控制者：需求方的现场用 `sudo su - app1`，个人场景用 `sudo su -`）。
- 非 UTF-8 的文件名（`ssh2` 收发文件名一律按 UTF-8 编解码，见第 7 节）。
- 远程条目的「缓存策略」四级（被方针「只在展开 / 选中时读取」取代，见第 5.6 节）。

### 反目标（即使能用也算失败）

- **导致账号被锁**：sudo 或登录的密码错误被自动重试；或一次输错被记为多次失败（第 5.4 节的实测坑）。
- 密码 / 私钥口令出现在渲染进程、日志、URI、命令行参数、错误信息中。
- 未经用户确认就接受主机密钥（`ssh2` 不设置 `hostVerifier` 时默认**自动接受**）。
- 向服务器写入，或以 sudo 身份执行读取以外的动作。
- 每读一个目录就在客户的 sudo 审计日志里留一条记录。
- 后台扫描把服务器或网络压垮（同一连接同时只有 1 个后台读取）。

## 3. 讨论中确认的事项（需求方，2026-11-22）

1. 先做 SFTP 只读；文件只做兜底的文件信息；放弃 SMB。
2. 缓存只在选中 / 展开目录时进行；定期扫描只对「建立索引」的目录。
3. 方案 A：主进程持有 SFTP 连接，扫描进程读远程目录时请主进程代读（第 4.1 节）。
4. 活动栏「远程连接」只做设定；文件树在资源管理器中。
5. 需要保活与超时重连。
6. 身份：公司场景 `sudo su - app1`（要密码）；个人场景 root + 个人用户；RHEL / Ubuntu / SUSE / Debian。
7. 先行试验用本机 WSL：用 `wsl --install` 装不同实例（不经 Microsoft Store），可以建用户、改 sudoers。
8. 暂不需要堡垒机。

## 4. 方案比较

### 4.1 远程目录的缓存放在哪里（需求方选定 A）

| 方案          | 内容                                                                                                               | 取舍                                                                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A（选定）** | 主进程持有 SSH 连接；扫描进程的远程枚举器把「列目录」请求发给主进程代读；缓存、调度、搜索沿用扫描进程与 `index.db` | 每台服务器一套连接；密码只在主进程解密；主机密钥确认在主进程弹出；搜索与「建立索引」直接可用。代价：扫描进程与主进程之间多一种往返消息（相对网络延迟可忽略），远程目录需要单独的调度规则 |
| B             | 扫描进程自己连 SFTP（主进程把解密后的密码交给它）                                                                  | 主进程取文件信息时还要再连一次（同一服务器两套连接）；主机密钥确认从两个进程发起；密码出现在两个进程中                                                                                   |
| C             | 远程缓存单独放在主进程，不进 `index.db`                                                                            | 结构独立，但调度、断开显示要重写一份，搜索也搜不到远程文件                                                                                                                               |

### 4.2 以其他身份读取的方式（控制者，讨论中已说明，先行试验已验证）

| 方案                                                                                                | 取舍                                                                                                                                                              |
| --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **在 SSH 连接上开命令通道，`sudo su - <目标>` 后 `exec sftp-server -R`，在该通道上走 SFTP（选定）** | 与现场的 `sudo su - app1` 一致，精确规则（只允许 `su - app1`）也能匹配；每打开一次通道 sudo 只记一行日志；`-R` 使服务器端只读。WinSCP 的「sudo 切换」也是同一思路 |
| 用 `sudo ls` / `find -printf` 等命令读目录并解析输出                                                | 每读一个目录 sudo 记一行日志（审计刷屏）；输出解析脆弱                                                                                                            |
| 直接以 app1 登录                                                                                    | 系统账号通常不能直接登录、没有密码                                                                                                                                |

### 4.3 SFTP 客户端库（控制者）

| 方案                                | 取舍                                                                                                                                                                                                                                                                                                       |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`ssh2`（直接使用，选定）**        | 纯 JS（可选的原生加速 `cpu-features` 不需要）；有 `keepaliveInterval` / `keepaliveCountMax`、异步 `hostVerifier`；同一连接上可开多个通道。第 5.4 节需要在命令通道上走 SFTP，只能借用其内部类 `ssh2/lib/protocol/SFTP.js`（先行试验已验证可行）——固定 `ssh2` 的精确版本，并把这部分收在一个文件里用测试兜底 |
| `ssh2-sftp-client`（doc 原计划）    | 是 `ssh2` 之上的 Promise 封装，不提供在命令通道上走 SFTP 的能力，第 5.4 节仍要直接用 `ssh2`；多一层依赖没有收益                                                                                                                                                                                            |

## 5. 设计

### 5.1 资源模型与 URI（控制者）

- 登录用户：`sftp://<connectionId>/<绝对路径>`，例：`sftp://3f2a…/var/log/app`
- 切换身份：`sftp://<目标用户>@<connectionId>/<绝对路径>`，例：`sftp://app1@3f2a…/opt/app1/log`、`sftp://root@3f2a…/root`
- authority 用 connectionId（doc 2.3 已有的原则：凭据与主机名不进 URI，改服务器地址只需改连接）；身份写进 URI 的 userinfo，**同一路径不同身份是不同的资源**（看到的内容可能不同，缓存分开）。目标用户与连接的登录用户相同时视为登录用户（不写 userinfo）。
- 路径：以 `/` 分段，每段用 `encodeURIComponent` 编码；根为 `sftp://<id>/`，经 `normalizeRootUri` 后为 `sftp://<id>`（`prefixOf` 补回 `/`，现有逻辑自洽）。
- **子项 URI / 父目录 / 名称的推导在 `packages/shared/src/vfs/` 中按 scheme 只定义一次**（不依赖 Node，渲染端、主进程、扫描进程共用；`file:` 继续用现有的 `pathToFileURL` 推导）。provider、扫描进程缓存键、渲染端 `descend`、搜索结果拼接必须逐字符一致（调研报告的最大风险，见第 6 节）。
- 隐藏文件：名称以 `.` 开头。名称区分大小写。
- 符号链接：`list` 不跟随（`kind: 'symlink'`），对链接再 `stat` 一次得到目标类型（与 LocalProvider 一致，`target: null` 为失效）；`stat` 跟随。

### 5.2 连接与凭据（控制者）

**表 `connections`**（迁移 0007；取代 doc 第 13 节的草案，删去 `kind` / `domain`）：

| 列                          | 说明                                                                                            |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| `id`                        | `crypto.randomUUID()`                                                                           |
| `name`                      | 显示名（例「顧客A 本番 AP1」）                                                                  |
| `host` / `port`             | 默认 22                                                                                         |
| `username`                  | 登录用户                                                                                        |
| `auth`                      | `password` / `key`                                                                              |
| `key_path`                  | 私钥文件的本地路径（`auth = key`；连接时读取，不复制）                                          |
| `secret`                    | safeStorage 加密：密码，或私钥口令（可空）                                                      |
| `sudo_secret`               | safeStorage 加密：sudo 用的另外的密码（空 = 用登录密码；SUSE 默认 `targetpw` 问的是 root 密码） |
| `identities`                | JSON 字符串数组：可切换的目标用户（`app1`、`root`…）                                            |
| `host_key`                  | 已信任的主机密钥（算法 + SHA256 指纹）；空 = 未信任                                             |
| `options`                   | JSON：`sftpServerPath`（空 = 自动探测）等                                                       |
| `auth_state`                | `ok` / `auth-failed` / `sudo-auth-failed`：认证锁定状态，**跨重启保留**（第 5.3 节）            |
| `created_at` / `updated_at` |                                                                                                 |

- 机密只在主进程：返回渲染端的 `ConnectionDto` 只有 `hasSecret` / `hasSudoSecret`；保存时渲染端传明文一次（经 IPC，不落日志），主进程立即加密。`safeStorage.isEncryptionAvailable()` 为 false 时拒绝保存机密（`CONN_SECRET_UNAVAILABLE`），不以明文保存。
- **一次连接只用一种方式提交一次密码**：`ssh2` 会依次尝试多种认证方式，密码错误时 `password` 与 `keyboard-interactive` 可能各记 1 次失败。用自定义 `authHandler`：按服务器提供的方式只选一种（优先 `password`，没有时 `keyboard-interactive`），失败即结束，不换方式再试（实施时用 sshd 日志 / `faillock` 确认只记 1 次）。
- 认证：密码（`keyboard-interactive` 时以密码作答）、私钥（OpenSSH / PEM 格式 + 可选口令；`.ppk` 是否可用实施时确认 `ssh2` 的 `parseKey`）。
- 删除连接：引用它的条目保留（显示「连接不存在」的错误行），删除前确认框显示被引用的条目数。

### 5.3 连接池、保活与重连（主进程 `modules/connection`，控制者）

- **每个连接一条 SSH 连接**，懒连接（第一次需要时才连）。其上：登录用户的 SFTP 子系统通道 1 个；每个使用中的切换身份 1 个通道（第 5.4 节）；身份切换时临时的进程轮询通道 1 个。注意 sshd 的 `MaxSessions`（默认 10）。
- **保活**：`keepaliveInterval` = 设置 `remote.keepaliveSec`（默认 15 秒），`keepaliveCountMax` = 3，约 1 分钟内发现静默断线（先行试验：5 秒 × 3 → 20.3 秒报 `Keepalive timeout`）。
- **空闲断开**：没有进行中的请求、且最近 `remote.idleDisconnectMin`（默认 5）分钟没有请求时断开（含 sudo 通道）；下次需要时重连（重连 = 再次 sudo，sudo 日志多一行）。
- **断线**：进行中的请求以 `FS_UNAVAILABLE` 失败（只读操作重复执行无副作用：连接池在**用户操作**发起的请求上自动重连并重试一次）；断开状态由扫描进程现有的可达性机制显示（第 5.6 节）。
- **重连时机**：用户操作（展开、选中、F5、测试连接）立即尝试；后台由扫描进程现有的离线探测退避（30 秒起翻倍、最长 5 分钟）驱动。
- **认证失败绝不自动重试**（反目标）：登录认证失败 → 该连接进入「认证失败」，此后所有请求直接以 `CONN_AUTH_FAILED` 失败、不连服务器，直到用户在「远程连接」视图中编辑连接或点「重新连接」。sudo 密码失败**按连接锁住所有切换身份**（`CONN_SUDO_AUTH_FAILED`；一个连接只有一个 sudo 密码，`pam_faillock` 按登录用户计数，按身份锁会让一个错密码在 app1 / app2 / root 上各试一次）；登录用户自己的 SFTP 不受影响。锁定状态写入 `connections.auth_state`，**应用重启后仍然有效**（否则每次启动时恢复的标签、展开的树与后台索引都会用过期的密码再试一次）；只有编辑连接（改了密码）或用户点「重新连接」才解除。
- **主机密钥**：`hostVerifier` 必须设置。第一次连接（任何触发来源）时主进程向窗口发确认请求，显示算法与 `SHA256:` 指纹；用户接受 → 保存到 `host_key` 并继续；拒绝 → `CONN_HOST_KEY_REJECTED`。确认框未回答时同一连接的其他请求等待（受各自超时约束）。已保存的指纹不一致 → 拒绝连接（`CONN_HOST_KEY_CHANGED`），「远程连接」视图显示新旧指纹，只能由用户明确「信任新的密钥」。
- **状态**：`idle` / `connecting` / `online` / `offline` / `auth-failed` / `host-key-pending` / `host-key-changed`，经事件 `connection.status` 推送到「远程连接」视图。

### 5.4 身份切换（先行试验已在 4 个发行版实测，控制者）

**sftp-server 的位置**：每次建立连接后以登录用户执行一次探测（不经 sudo，不留 sudo 日志）：依次检查 `/usr/libexec/openssh/sftp-server`（RHEL 系）、`/usr/lib/openssh/sftp-server`（Debian / Ubuntu）、`/usr/libexec/ssh/sftp-server`（openSUSE Leap 16）、`/usr/lib/ssh/sftp-server`，取第一个可执行的；连接设置可指定路径（覆盖探测）。

**打开一个切换身份的通道**（非终端方式，默认）：

1. 开命令通道，执行（目标用户与 sftp-server 路径先按白名单正则校验；密码**绝不**进命令行）：
   `printf 'PCHPID:%s\n' $$ >&2; exec sudo -k -S -p '<提示标记>' su - <目标>`（目标为 root 时 `su -`）
   — `$$` 即随后被 `exec` 替换成的 sudo 的 PID。
2. 同时开一个轮询通道，每约 150ms 读一次进程表（`ps -eo pid=,ppid=,comm=`），**sudo 的子孙中出现 `su` 进程 = 认证成功**（PAM 认证在 sudo 进程内完成，成功后才 fork）。轮询从第 1 步之后就开始：`NOPASSWD` 的环境没有提示也能判定成功。**前提检查**：每次建立连接后（与 sftp-server 探测一起）确认登录用户能在进程表中看到 root 的进程（例如 PID 1）。看不到（`/proc` 以 `hidepid=2` / `invisible` 挂载的加固环境）时无法判定成功，**不执行 sudo**，切换身份一律以 `CONN_PROCESS_LIST_HIDDEN` 失败并说明原因（控制者：不提供按时间猜测成功的退路——判错会回到「一次输错记 2 次」）。
3. stderr 出现提示标记 → 写入密码 + 换行（一次）。**再次出现提示 = 密码错误**：立即关闭通道，按连接锁住所有切换身份（`CONN_SUDO_AUTH_FAILED`，第 5.3 节），不重试。
4. 判定成功后，向目标用户的 shell 写入：`printf '\120CHSTART\n'; exec <sftp-server> -R`
5. 跳过标记 `PCHSTART` 之前的所有输出（登录脚本的欢迎信息、「Last login」等），之后的字节交给 SFTP 客户端（`ssh2` 的 SFTP 类桥接到该通道）。
6. 失败分类：stderr 含「not allowed / not in the sudoers / may not run」→ `CONN_SUDO_DENIED`；含「must have a tty」→ 改用终端方式（下）并记住该「连接 + 身份」的方式；通道在标记出现前关闭（如目标账号 shell 为 nologin）或 15 秒超时 → `CONN_SUDO_FAILED`（附 stderr 摘要，过滤掉密码）。

**终端方式**（`requiretty` 的环境）：同上，但通道申请伪终端，提示与输出都从 stdout 来；第 4 步前先执行 `stty raw -echo -ixon -ixoff -isig -icanon -opost min 1 time 0`。

**为什么必须先判定成功再写命令行**（实测）：密码后紧接着写命令行时，密码错误会让 sudo 把命令行当成第二次密码，**一次输错记 2 次失败**（sudo 日志 `2 incorrect password attempts`）；开了 `pam_faillock`（连续 3 次锁定）的环境会很快锁号。「先 `sudo -v` 再复用凭据」不可行：没有 tty 时 sudo 不缓存凭据。

**sudo 密码**：默认用登录密码；连接设置可另设（SUSE 的 `targetpw` 默认问 root 密码）。私钥登录且未设 sudo 密码时：sudo 若要求密码则以 `CONN_SUDO_AUTH_FAILED` 失败（不写入任何东西）。

**只读**：`sftp-server -R`（实测以 root 身份写入也被拒绝），且 provider 只发读取类请求（OPEN 只读 / READ / CLOSE / OPENDIR / READDIR / STAT / LSTAT / REALPATH / READLINK）。

**通道生命周期**：第一次用到该身份时打开，随 SSH 连接存续；通道意外结束（sftp-server 退出）时下一次请求重开一次。

### 5.5 SftpProvider（主进程 `vfs/providers/sftp.provider.ts`，控制者）

- `scheme: 'sftp'`；`stat`、`list`；`read` / `createReadStream` 本次不提供（以 `FS_UNSUPPORTED` 类错误拒绝，文件不打开内容）。
- 经连接池取得「连接 + 身份」对应的 SFTP 客户端；连接池通过构造参数注入（`main-vfs` 不能 import `main-module`，由 bootstrap 组装）。
- 错误映射：SFTP 状态码 2 → `FS_NOT_FOUND`、3 → 权限不足（沿用现有拒绝访问的错误码）、连接类错误 → `FS_UNAVAILABLE`、超时 → `FS_TIMEOUT`、认证 / 主机密钥 / sudo → 对应 `CONN_*`。
- `list` 同时从 `longname`（`ls -l` 形式）的第 3 列取属主名，供「无权限」提示（第 5.8 节）；取不到时省略。

### 5.6 扫描进程中的远程目录（需求方的缓存方针，控制者的具体化）

- **远程枚举器**：按 scheme 分派的复合枚举器，`sftp:` 交给远程枚举器，它把「列目录」经新消息发给主进程（`remote.op { id, op, uri }` → `remote.opResult { id, ok, result | error }`，取消经 `remote.cancel { id }`），主进程用 SftpProvider 执行。
- **位置**：新增第三种位置 `remote`（`RootConfig.location`、超时 `vfs.timeoutSec.remote`（默认 20 秒）、后台休息 `cache.backgroundGapMs.remote`（默认 500ms））；`shareKey` / `hostKey` = `sftp://<connectionId>`（一条 SSH 连接是一个可达性单位与并发单位：同时 1 个用户读取 + 1 个后台读取）。
- **读取时机**（需求方方针）：
  - **会读取**：展开目录、选中目录、标签中新显示的目录（P0：有缓存先显示缓存，再读一次服务器，有变化才通知；2 秒去重沿用），F5 / 刷新按钮 / 状态行「重试」（强制）。
  - **不读取**：关注点 / 近层 / 远层的定期确认、热点、窗口重新获得焦点、滚回视口（控制者：这些都不是「选中或展开」）。
  - **后台**：只对「建立索引」的目录（整棵子树），每个目录距上次读取超过 `cache.remoteIndexIntervalMin`（默认 30 分钟）才再读；同一连接同时 1 个。
- **检查 = 重新列出**：远程目录不比较目录修改时间，每次都完整列出（doc 8.3 已有的方针；也避免文件大小变化而目录修改时间不变的漏检）。
- **缓存策略**：远程条目不适用四级策略，右键菜单中隐藏「缓存策略」，保留「建立索引」。
- **断开**：沿用现有可达性机制（`FS_UNAVAILABLE` / 探测超时 → 离线 → 显示缓存与断开图标 → 退避探测，探测即重连）。`CONN_AUTH_FAILED` / `CONN_HOST_KEY_*` / `CONN_SUDO_*` **不算断开**（显示错误行，指引到「远程连接」视图），也不进入退避探测。
- **搜索**：缓存过的远程条目照常可搜索，结果的定位走现有导航。

### 5.7 主进程的访问范围（M1-K17 的 sftp 部分，控制者）

M1-K17（主进程只接受工作区条目之下的 URI）尚未实现。引入远程连接时，**`sftp:` URI 必须在某个工作区的远程 folder 条目之下**（或恰为远程 file 条目，本次不提供），否则以 `IPC_FORBIDDEN` 拒绝：`vfs.*`、`doc.*`、`system.*`、`launcher.*` 的入口统一检查。连接管理的通道按 connectionId 操作，不受此限。`file:` 部分的 K17 仍按原计划处理（不在本次范围）。

### 5.8 界面（控制者，需求方确认了分工）

**活动栏「远程连接」视图**（替换现有占位 `SidebarEmptyState`）：

```
远程连接                         [+ 新建]

  身份: app1  root                 [测试] [编辑] [删除]
```

- 状态点：在线 / 未连接 / 断开 / 认证失败 / 主机密钥待确认 / 主机密钥已变化。
- 编辑对话框：名称、主机、端口、用户名、认证方式（密码 / 私钥：路径 + 口令）、可切换身份（标签输入）、sudo 密码（同登录密码 / 另外设置）、sftp-server 路径（自动 / 指定）、已信任的主机密钥（只读显示 +「信任新的密钥」）。
- 「测试连接」逐步显示：连接 → 主机密钥 → 认证 → SFTP → 每个身份的切换结果（含探测到的 sftp-server 路径与采用的方式「非终端 / 终端」）。**第一次 sudo 认证失败即停止**，不再测试其余身份（否则一次点击就可能凑满 3 次失败）。

**资源管理器**：

- 添加入口：树空白处右键菜单与空状态增加「添加远程文件夹…」：对话框选连接（旁边「管理连接」跳到「远程连接」视图）、身份（登录用户 + 连接登记的身份）、路径（默认：登录用户为其 home 目录（`realpath('.')`），其他身份为 `/`）；确认时 `stat` 必须是目录。条目标签默认为路径最后一段（与本地一致）。
- 远程条目的图标区别于本地（如 `ServerIcon` 叠加）；断开图标沿用（渲染端 `shareKeyOfUri` 等按 scheme 处理）。
- 右键菜单：隐藏「在资源管理器中显示」「缓存策略」；「复制路径」复制服务器上的绝对路径（`/opt/app1/log`），另有「复制 URI」保持现状。
- **「无权限」提示**：目录读取得到权限不足时，状态行显示「无权限」；若属主（第 5.5 节）在该连接登记的身份中，状态行给出「以 app1 身份添加为条目」（新条目加在同一分组下）。不自动切换身份（审计上要能说清谁用 sudo 读了什么）。

**标签与预览**：

- 远程目录在标签中用 folder 插件显示（经 `vfs.list`）。
- 远程文件只匹配兜底插件：office / html / markdown / text 插件的 manifest 声明 `schemes: ['file']`；兜底插件对非本地资源隐藏「用系统应用打开」「在资源管理器中显示」「作为文本查看」（SDK 增加判断资源是否本地的能力，具体 API 留给实施者）。
- 地址栏 / 文件信息的显示路径：`<连接名>:<绝对路径>`，切换身份时 `<身份>@<连接名>:<绝对路径>`。

### 5.9 设置、错误码、IPC（控制者）

- 设置新增：`remote.keepaliveSec`（15，5–120）、`remote.idleDisconnectMin`（5，1–60）、`vfs.timeoutSec.remote`（20，5–120）、`cache.backgroundGapMs.remote`（500）、`cache.remoteIndexIntervalMin`（30，5–1440）。现有 `remote.cacheSizeMB` 暂无用途（下载缓存不在本次范围），保留并记录。
- 错误码新增：`CONN_NOT_FOUND`、`CONN_AUTH_FAILED`、`CONN_HOST_KEY_REJECTED`、`CONN_HOST_KEY_CHANGED`、`CONN_SUDO_AUTH_FAILED`、`CONN_SUDO_DENIED`、`CONN_SUDO_FAILED`、`CONN_SFTP_SERVER_NOT_FOUND`、`CONN_PROCESS_LIST_HIDDEN`、`CONN_SECRET_UNAVAILABLE`（三种语言的文案同时添加）。
- IPC：`connection.list` / `save` / `delete` / `test` / `reconnect` / `trustHostKey`；事件 `connection.status`、`connection.hostKeyPrompt`（渲染端回答经 `connection.answerHostKey`）。`entry.add` 的 `uri` 接受 `sftp:`（经连接存在性与 `stat` 校验；`rejectTemporary` 只对 `file:` 生效）。

### 5.10 结构（控制者）

- 主进程：`modules/connection/`（repo、service、连接池、身份切换、主机密钥确认、ipc）；`vfs/providers/sftp.provider.ts`（连接池以接口注入）；`vfs/location.ts` / `scanner-config.ts` 支持 `remote`；bootstrap 组装并在连接变化时重新下发扫描配置。
- 扫描进程：复合枚举器 + 远程枚举器；`childUri` / `parentUri` / `parentOf` / `isValidUri` / `needList` / 并发与看门狗按 scheme 处理（并发以 socket 为前提，中止的请求由主进程丢弃结果）。
- 共享：URI 推导、协议消息、设置、错误码、IPC 契约。
- 渲染端：`features/connections`（视图与对话框）；explorer 的添加对话框经 `data/connections.ts` 取连接列表（feature 之间不互相 import）；`lib/file-uri.ts` / `logical-path.ts` / `query-client.ts` 按 scheme 处理。
- 依赖：`ssh2`（精确版本）；内部类的借用只在 `modules/connection` 的一个文件中。

## 7. 先行试验（2026-11-22，WSL，用完即弃的脚本）

环境：Ubuntu 26.04（sudo-rs 0.2.13、OpenSSH 10.2）、Debian 13（sudo 1.9.16、OpenSSH 10.0）、AlmaLinux 9.9（sudo 1.9.17、OpenSSH 9.9）、openSUSE Leap 16.1（sudo 1.9.17、OpenSSH 10.3），均以 `wsl --install -d <名称> --no-launch` 安装；sshd 端口 2201–2204；试验用户 `pchuser` / `app1` / `app2`；`ssh2` 1.17.0。环境的配置脚本保存在 `scripts/wsl-sftp/`（实施与手动验证复用）。

## 9. 需求方的回答（2026-11-22）

- **连接密码只做「保存」**（需求方）：不提供「不保存，连接时询问」。密码、私钥口令与 sudo 密码按第 5.2 节以 safeStorage（Windows 上为 DPAPI）加密后保存在本机数据库；后台的建立索引扫描与断线重连因此可以在无人操作时进行。客户的安全规定要求不在终端保存密码时，再作为单独的需求追加（届时需要：主进程向窗口询问密码的流程、只在内存中保存且有有效期的凭据、没有凭据时跳过后台读取）。
